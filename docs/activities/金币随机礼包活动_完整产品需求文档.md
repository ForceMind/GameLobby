# 金币随机礼包活动｜产品需求文档

> 修订：2026 年 10 月 21 日按评审结论修订，主要是净消耗口径纳入明日宝箱（见同目录 REVIEW.md）。

## 一、功能概述

金币随机礼包是一项面向符合近期**游戏净消耗**条件的用户开放的充值活动。

运营分别配置基础充值档位和额外赠送档位，随机组合生成候选礼包，经人工选择后发布。服务器依据用户最近指定时间内的**资格净消耗**、个人购买冷却和礼包状态，筛选可用组合，再为用户分配当前可购买的礼包。资格净消耗等于支出减获得：支出包括游戏投入和明日宝箱的买箱；获得包括游戏结算获得、明日宝箱的奖励和过期退款、本活动实际发放的额外赠送金币。

正常展示数量为 0、2 或 4 个。礼包购买成功后从当前列表消失，并进入该用户的个人冷却池，冷却 48 小时。冷却结束后，礼包仍需重新通过资格筛选和展示分配，才可以再次购买。

**业务主流程：配置档位 → 随机生成备选组合 → 人工选择上线 → 按资格净消耗筛选候选池 → 分配当前礼包 → 创建支付订单 → 支付确认成功 → 发放金币、赠送部分计入收益抵减资格净消耗，同时进入个人冷却 → 重新计算候选池并补位 → 冷却结束后重新参与资格筛选。**

### 1.1 规则口径

48 小时个人购买冷却及额外赠送金币抵减资格消耗均为本活动的正式业务规则。本文对尚未明确的边界给出统一的产品默认建议，包括收益统计口径、同一礼包识别、支付锁定、退款后的冷却、部分礼包到期和缩减展示状态；这些建议属于产品方案，不代表现有系统已经实现或通过支付测试。

核心原则：

1. 满足消耗门槛，只代表可以进入候选池，不代表可以直接购买。
2. 新建购买订单时，礼包必须属于服务器当前分配给该用户的有效展示记录。
3. 同一用户对同一礼包成功购买后，48 小时内不能再次购买；不采用“本活动版本只能购买一次”的永久排除规则。
4. 支付成功后的履约依据合法订单的锁定内容，不再取决于礼包是否仍在当前页面上。
5. 24 小时展示有效期与 48 小时购买冷却分别计时，互不替代。
6. **基础充值金币不抵减资格净消耗；本活动实际到账的额外赠送金币，以及明日宝箱的奖励和过期退款，都作为金币收益抵减，每笔只能抵减一次。**
7. 赠送到账后要先更新资格净消耗，再决定是否保留其他礼包、展示 0/2/4 个以及允许新建订单。

## 二、关键概念

| 概念 | 定义 |
|---|---|
| 基础充值档位 | 支付币种、支付金额以及基础获得金币的配置 |
| 额外赠送档位 | 赠送金币数量，以及与该档位一一对应的资格净消耗门槛 |
| 资格净消耗 | 指定滚动窗口内的支出（有效游戏金币支出、明日宝箱买箱），减去同期获得（游戏获得金币、明日宝箱奖励和过期退款、本活动实际发放的额外赠送金币），再与 0 取较大值 |
| 额外赠送抵减流水 | 每笔成功发放的额外赠送金币对应的唯一收益记录；用于抵减资格净消耗、审计和退款冲正 |
| 礼包组合 | 一个基础充值档位与一个额外赠送档位组成的商品 |
| 稳定礼包身份 | 用于识别同一商品、去重和关联购买冷却的长期身份，不随展示、订单或配置版本重建 |
| 配置版本 | 礼包某次发布时的价格、奖励、资格门槛等内容快照 |
| 用户候选池 | 当前已上线、用户达标、非冷却且没有其他不可售限制的不同礼包集合 |
| 当前展示记录 | 服务器实际分配给该用户的一次礼包展示授权，记录所属用户、礼包身份、配置版本和有效期 |
| 个人冷却池 | 记录该用户哪些礼包仍处于购买后 48 小时冷却中 |
| 缩减展示状态 | 候选仅有 4 个而无法引入新礼包时，将展示从 4 个调整为 2 个，并暂时保持 2 个的服务端状态 |
| 支付锁定 | 合法订单正在确认支付结果时，临时阻止重复下单的状态，不等于购买冷却 |

“候选资格”“展示授权”“支付订单”是不同层级的记录，不能只用一个礼包 ID 代替全部购买判断。

## 三、后台基础配置

### 3.1 活动参数

| 参数 | 产品口径 |
|---|---|
| 活动开关 | 支持开启、暂停、关闭 |
| 净消耗统计周期 | 后台可配置，示例为最近 7 × 24 小时；支出（含宝箱买箱）、游戏获得、宝箱奖励与过期退款、本活动额外赠送使用同一窗口 |
| 额外赠送抵减规则 | 本活动实际发放的额外赠送金币全额抵减；基础充值金币不抵减 |
| 资格净消耗下限 | 0；计算结果为负数时按 0 参与门槛判断 |
| 单次礼包展示有效期 | 24 小时 |
| 已购礼包个人冷却 | 48 小时 |
| 正常展示数量 | 仅 0、2、4 个 |
| 同用户待支付订单 | 默认同一活动同时最多 1 笔，防止并发购买和复杂占位 |
| 订单支付期限 | 由接入的支付流程确定并在创建订单时锁定；产品建议初始设置为 15 分钟，接入时须验证可执行性 |
| 缩减展示状态持续时间 | 最长 24 小时；候选集合实质变化时可以提前结束 |
| 用户完整候选池 | 仅服务器和有权限的后台可查询，不下发全部购买入口给前端 |

24 小时和 48 小时均为连续时长，不按自然日零点重置。所有资格、有效期和冷却判定均以服务器时间为准。本活动不依赖自然日边界，时区不影响资格、有效期和冷却；后台按日统计时，按用户所属运营大区的时区分日。

### 3.2 基础充值档位

| 档位示例 | 支付金额 | 基础金币 |
|---|---:|---:|
| B01 | USD 1.00 | 10,000 |
| B02 | USD 5.00 | 60,000 |

基础档位可以批量配置。每个档位明确币种、支付金额、基础金币、启停状态。金额采用该币种支持的合法支付精度，金币为整数。

### 3.3 额外赠送档位

每个赠送档位必须同时配置赠送金币数和触发消耗门槛，不允许缺失对应关系。

| 档位示例 | 额外赠送金币 | 最近统计周期内资格净消耗门槛 |
|---|---:|---:|
| G01 | 500 | 10,000 |
| G02 | 1,000 | 50,000 |
| G03 | 2,000 | 100,000 |
| G04 | 5,000 | 200,000 |
| G05 | 10,000 | 运营另行配置，缺失时不得发布 |
| G06 | 100,000 | 运营另行配置，缺失时不得发布 |

基础金币、赠送金币及各门槛须通过有效性校验。示例不是完整生产配置，不自动推断未给出的门槛。后文计算示例里用到的赠送数值（如 50,000）只是演示，不一定是上表里的档位。

## 四、组合生成、发布与同一礼包识别

### 4.1 组合计算

一个礼包由一个基础档位与一个赠送档位组成：

- 支付金额 = 基础档位支付金额。
- 总到账金币 = 基础金币 + 额外赠送金币。
- **资格净消耗**门槛 = 所属赠送档位对应的门槛。

例如：USD 1.00 购买基础 10,000 金币，搭配赠送 100,000 金币，最终得到 110,000 金币。用户必须达到该 100,000 金币赠送档位所配置的消耗门槛，才可能获得这个组合。

### 4.2 一键随机生成与人工发布

运营选择基础档位范围、赠送档位范围和目标数量，后台从可用配对中随机生成不重复的备选组合。

随机生成只产生待选择的组合，不自动上线。运营查看支付金额、基础金币、赠送金币、总金币、门槛和单位支付金额对应金币数，人工勾选后发布。

基础档位数乘以赠送档位数是配对数量的理论上限；剔除重复商品、无效配置和运营未选中的组合后，实际可上线数量可能更少。

同一商品只保留一个有效可售版本，不允许通过重复生成相同组合放大其被抽中的概率。

### 4.3 稳定礼包身份与冷却归属

购买冷却按“用户 + 稳定礼包身份”记录，而不是按某次展示记录、订单 ID 或配置版本记录。

默认将**支付币种、支付金额、最终到账奖励内容完全相同**的配置视为同一礼包。只有金币奖励时，以币种、支付金额、总到账金币判断商品是否相同。

下列操作不得把同一礼包变成一个没有购买历史的新礼包：

| 操作 | 是否清除原购买冷却 |
|---|---|
| 修改标题、图片、排序或标签 | 否 |
| 重新随机生成相同商品、换一个组合配置 ID | 否 |
| 下架后重新上架、发布新的活动配置版本 | 否 |
| 调整用户消耗门槛 | 否 |
| 调整基础金币与赠送金币的拆分，但支付金额和总奖励不变 | 否 |

如果支付价格或最终奖励发生实质变化，可以形成新的商品身份。普通配置操作不能隐式清空个人冷却；历史购买与冷却记录需要持续关联同一商品及其后续发布版本。

同一个基础充值档位搭配不同赠送数量，若形成不同的最终奖励，则属于不同礼包，各自冷却。此规则不等于“购买任何礼包后，整个活动关闭 48 小时”，也不等于“相同赠送档位的所有价格组合共同冷却”。

### 4.4 发布版本与已有订单

价格、奖励、门槛等配置以发布版本固定。编辑先产生待发布内容，经人工发布后生效。

新版本影响的旧展示记录应失效或重新分配；前端需要获取新内容后才可发起新订单。未变更的礼包不因其他礼包发布而被无故重新随机。

同一稳定礼包身份的冷却继续沿用。已合法创建、仍有效的订单使用创建订单时锁定的币种、金额、基础金币、赠送金币和总奖励，不追溯改价或改奖。

活动暂停或礼包下架，停止新的展示授权和新建订单；已经合法创建的订单按其有效支付规则处理。异常订单需要退款时进入明确的退款流程，不直接丢弃实际支付结果。

## 五、资格净消耗与用户候选池

### 5.1 计算口径

礼包资格不再按游戏金币总支出直接判断，而是按**资格净消耗**判断：

> **资格净消耗 = max(0，A − B − C)**
>
> - **A：窗口内的支出**，包括已确认结算的游戏金币扣除额，以及明日宝箱的买箱支出。
> - **B：窗口内的获得（游戏和宝箱）**，包括游戏结算返还、获胜金币，以及明日宝箱实际到账的奖励和过期退款。
> - **C：窗口内本活动已实际发放的额外赠送金币**，按实际发放记录累计。

和明日宝箱文档是同一套口径：宝箱文档的 G 就是这里的 A，W 是这里 B 里的游戏部分，宝箱文档的 C 等于这里 B 里的宝箱部分加上这里的 C。

A、B、C 使用**同一个后台配置的滚动统计周期**，例如最近 7 × 24 小时，以服务器当前时间为基准，不按自然周清零。

- 游戏赢得或返还的金币计入 B，抵减已发生的游戏支出。若 A 记录的是全部下注/扣款额，B 就记录相应的全部结算返还，包括赢回的本金；不得既使用“净亏损”作为 A，又额外扣除同一笔结算返还。
- 明日宝箱：买箱的金币计入 A；开箱奖励到账后计入 B（奖励里含买箱的本金，所以买箱和这部分本金互相抵掉）；宝箱过期后系统自动退回的购箱本金，在退款到账时计入 B。宝箱“本可获得”但没有领取的预计算奖励不计入。
- **礼包基础充值金币不是收益，不计入 B 或 C，不抵减资格净消耗。**
- **本活动额外赠送金币视为金币收益，计入 C，立即降低资格净消耗；不是视为新的游戏支出，也不会增加 A。**
- 其他来源的充值、转账、提现，以及除明日宝箱外的其他活动赠送（签到、转盘、任务、月卡等），默认不计入 B 或 C；如将来需要纳入，必须增加独立、明确的活动口径并避免与已有收益重复。
- 有效游戏与本活动赠送的每笔流水只计一次。取消、撤销、无效对局、错误赠送、冲正和回滚必须同步修正对应金额。
- 负数结果不产生负门槛，统一按 0 计算；但后台可以保留未截断的 A − B − C 原值便于核对。

### 5.2 计算示例

假设统计周期为最近 7 天：

| 项目 | 金币 | 进入公式 |
|---|---:|---|
| 游戏累计有效扣除 A | 200,000 | +200,000 |
| 游戏结算获得 B | 80,000 | −80,000 |
| 已到账的本活动额外赠送 C | 30,000 | −30,000 |
| **最终资格净消耗** | **90,000** | **max(0, 200,000 − 80,000 − 30,000)** |

此时用户满足 10,000、50,000 的资格门槛，不满足 100,000、200,000 门槛。即使游戏总支出达到 200,000，也不能按照总支出误判为全部达标。

再加一个宝箱的例子：同期买箱 500 计入 A（A 变成 200,500），开箱得到 700（500 本金 + 200 额外）计入 B（B 变成 80,700），净消耗是 200,500 − 80,700 − 30,000 = 89,800，只比不算宝箱时少了额外的 200。

再例如，用户最初 A − B = 120,000，满足 100,000 的赠送资格；购买了一个额外赠送 50,000 金币的礼包且赠送到账后，资格净消耗变为 **70,000**。对应 100,000 门槛的其他尚未购买礼包应立即失去资格，而非等 24 小时轮换或 48 小时冷却结束。

### 5.3 本活动额外赠送到账与资格变化

1. 用户创建订单时，依据**下单当时**的资格净消耗和展示授权校验合法性。
2. 订单合法支付成功后，按订单快照发放基础金币与额外赠送金币。两部分在同一次入账里一起进钱包，不分开到账（这是前提，接入钱包时确认）；记录里分成两行，是为了只拿赠送部分抵减。
3. **入账成功时**，在同一次提交里生成一笔对应的资格抵减流水，记入 C；同一订单的同一份赠送只能抵减一次。
4. 赠送到账后立刻重新计算资格净消耗、冷却和全部候选，不等到下一次 24 小时轮换。
5. 原展示的其他礼包如果已跌出门槛，立即移除其展示授权；保留仍达标的礼包，再按 0/2/4 数量规则重新分配，不能强行保留四张。
6. 发生资格下降时，**已合法创建且仍允许付款的旧订单仍按锁定快照履约**；新建订单必须采用资格变化后的最新结果。
7. 入账完成之前，订单一直占着支付锁定（见第九章），该用户不能新建其他订单；所以不会出现“钱已付、赠送还没抵减、又用旧资格去买”。

购买成功通常同时产生两种彼此独立的效果：**对已购礼包开启 48 小时个人冷却**，以及**额外赠送金币抵减全活动共用的资格净消耗**。后者可能令许多不同的礼包同时失去资格，不能仅移除已购礼包然后机械补满四个。

### 5.4 窗口时间、反向调整与防重复

- 游戏支出与游戏获得，以业务确认的有效游戏结算时间计入对应窗口；宝箱买箱按扣款时间、宝箱奖励和过期退款按实际到账时间计入；本活动额外赠送按**实际到账记账时间**计入对应窗口。
- 当某笔记录滚出窗口时，其对 A、B 或 C 的影响分别自然消失。**赠送抵减不是永久扣除**；如果奖励滚出最近 7 天，而同期其他有效游戏记录仍在窗口，资格净消耗可能回升。
- 撤销某笔曾计入的支出、游戏返还或赠送，应按原流水更正，不能额外产生一笔新的同类收益或重复扣除。
- 退款后若赠送金币被合法追回，应对相应 C 流水进行冲正并重算资格，避免“赠送已追回、资格还被永久抵减”；若赠送未追回，则不能无依据地取消这笔实际已得金币收益。退款**不清除或重启**对应已发生的 48 小时购买冷却。
- 同一订单补发、消息重试、设备切换、重复页面刷新，均不得让 C 再增加一次。
- 用户后来把获赠金币用于游戏，只有实际发生且有效结算的游戏扣款才增加 A，游戏对应获得仍进入 B；**不能仅凭收到或持有金币就增加游戏消耗**。

### 5.5 资格门槛的使用方式

所有已上线赠送档位的门槛均与**当前资格净消耗**比较。净消耗达到较高门槛时，同时满足所有不高于该值的低门槛，不采用互斥区间。

资格净消耗是滚动计算指标，不是购买时额外扣除的可兑换余额。**不能在已经把赠送金币计入 C 后，再按礼包门槛从净消耗里扣减一次**；否则会双重扣除。

用户资格会随以下事件变化：游戏支出、游戏结算获得、额外赠送到账及冲正、历史流水滚出窗口、活动统计周期/门槛配置调整。普通页面刷新只重新核验，不重复增加或扣除任何流水。

### 5.6 当前可用候选池

一个礼包进入用户候选池，必须同时满足：

1. 活动开放，礼包已发布且可售，配置完整有效。
2. 用户**当前资格净消耗 ≥ 该礼包所属额外赠送档位的门槛**。
3. 该用户对该稳定礼包身份不处于 48 小时购买冷却。
4. 不存在未处理的该礼包履约异常、其他支付锁定或其他明确的不可售限制。

候选数按去重后的稳定礼包身份计算，不按配置行数、展示记录数或同一商品的不同版本计算。

**候选池不是购买列表**。没有当前有效展示授权的候选礼包仍然不能直接下单。购买后应先按新的 A、B、C 重新筛选完整候选池，再判断当前正常展示目标是 0、2 还是 4。

## 六、个人冷却池

### 6.1 进入条件与时间

服务器首次核验一笔合法订单支付成功时，记录购买成功时刻 T，并将该礼包放入购买人的个人冷却池。

> 冷却开始时间 = 服务器首次确认该合法订单支付成功的时间。  
> 冷却结束时间 = 冷却开始时间 + 48 小时。

渠道返回的支付完成时间（paid_at）另外记录，只用来判断订单是不是在有效期内，不用来起算冷却。

服务器当前时间早于冷却结束时间时，该礼包不能进入该用户的可分配候选池；达到或晚于结束时间时，冷却限制结束。

重复通知、页面刷新、重新登录、设备切换、补发金币、普通配置修改，均不重新起算或延长这 48 小时。

例如 10 月 15 日 10:00 确认购买成功，冷却结束时间是 10 月 17 日 10:00。

### 6.2 冷却中的行为

购买成功的展示授权失效，礼包从正常可售列表消失。即使该用户的**抵减后资格净消耗**仍达到原门槛，也不得补回同一礼包、重新分配其等价版本或通过直接请求创建新订单。其他礼包如因额外赠送抵减而跌出门槛，也应立即移除。

用户可以继续购买当前被分配的其他不同礼包。其他用户不受该用户冷却影响。

### 6.3 冷却结束

冷却结束只表示解除该项购买限制，不保证礼包重新出现。

服务器仍需检查礼包是否上线、活动是否开放、用户是否达标及是否存在其他限制。只有通过检查，才重新进入候选池；进入候选池后还必须经过展示分配。

冷却结束后若页面原有礼包仍有效且展示名额已满，可以保持原列表，不强制将刚结束冷却的礼包顶替进来。若名额不足，可以参与补位；到期轮换时可以参与随机分配。

冷却状态结束不删除历史购买、订单和冷却记录。

### 6.4 不进入冷却的情况

以下行为本身不触发 48 小时购买冷却：仅进入页面、点击购买但未成功支付、支付失败、支付终态取消、展示到期、被轮换替换、因数量规则隐藏、资格不再满足、运营下架。

这些情况是否可重新展示，分别依据当前资格、发布状态和展示分配规则判断。

### 6.5 已支付但未到账、退款与异常

| 情况 | 处理规则 |
|---|---|
| 支付成功，金币正常到账 | 进入 48 小时冷却；实际发放的额外赠送计入 C，先降低资格净消耗、重新筛选，再决定是否补位 |
| 支付成功，但整单入账还没完成（钱包故障或超时） | 支付成功仍然成立并记录冷却；订单继续占着支付锁定，该用户不能新建其他订单；按原订单重试入账或人工处置，入账成功后同一次提交里生成 C 流水，再重新筛选 |
| 超过 48 小时但原订单发奖仍未完成 | 48 小时冷却不被伪造延长；该礼包另受“履约异常未解决”限制，解决后再参与候选筛选 |
| 已履约订单之后退款 | 按奖励是否实际追回冲正对应赠送抵减流水并重新计算资格；不自动提前清除、重启或延长原 48 小时冷却 |
| 支付结果重复到达 | 只处理首次合法状态变化，不重复发奖，也不重新延长冷却 |
| 订单不符合有效支付条件但实际产生扣款 | 进入异常收款核对及退款流程，不作为正常礼包购买发奖，不生成正常购买冷却 |

退款后冷却继续按原成功时间计算。异常账户可能另有独立限制，但不能把其他限制伪装成购买冷却。

## 七、展示数量与排序

### 7.1 正常数量

N 为当前可用候选池中不同礼包的数量，已经排除购买冷却等不可售项目。

| 可用候选数 N | 正常展示数 |
|---:|---:|
| 0～1 | 0，显示“暂无礼包” |
| 2～3 | 2 |
| 4 个及以上 | 4 |

不在正常可售状态下展示 1 个或 3 个礼包。用户支付结果确认中的页面是独立的暂态，按第九章处理。

### 7.2 购买后的数量变化

用户只有 A、B、C、D 四个候选，且当前全部展示。假设**额外赠送抵减后的资格净消耗仍使 B、C、D 达标**，购买 A 后：

- A 进入个人冷却池，当前候选变为 B、C、D 三个。
- 页面只能显示其中两个，例如 B、C。
- D 因数量规则暂时隐藏，仍在候选池内，不进入购买冷却。
- D 未再次被分配前，用户不能直接调用接口购买 D。

如果原来只有两个候选，购买其中一个后经赠送抵减与冷却排除只剩一个可用候选，正常礼包区显示“暂无礼包”。该剩余礼包并非被标记为已购买或冷却，而是因不足两款暂不展示。

### 7.3 保留、缩减与排序

普通刷新优先保留仍有效且**资格净消耗依旧达标**的已有展示，不因重复进出页面改变选择。

当需要从多个有效旧礼包中缩减数量时，优先保留剩余展示有效期较长的礼包；相同有效期时按已有稳定顺序保留。一次确定并存储结果，不在每次刷新时重复随机选择被隐藏者。

页面按支付金额由低到高排序；支付金额相同时按总到账金币由少到多排序；仍相同时采用固定次级顺序。

本方案允许同时出现多个价格相同但奖励不同的礼包。“价格从低到高”只是排序，不自动表示四个互不相同的价格档位。若要强制价格梯度，需要另行增加选取约束，并重新定义不足四档时的数量规则。

## 八、24 小时有效期、随机替换与缩减展示

### 8.1 单礼包有效期

每次新分配或到期后重新分配一个礼包，建立新的展示记录：

> 本次展示到期时间 = 本次分配时间 + 24 小时。

补位礼包从补位时独立开始计时。其他被保留礼包的原分配时间和到期时间不变。

24 小时是单次展示授权的最长有效期，不是保证至少展示 24 小时。购买、资格失效、下架、配置变化及数量缩减均可提前终止展示。

正常刷新、切回页面、心跳请求以及其他礼包购买成功，不能把所有保留礼包的有效期统一重新延长 24 小时。

前端不展示该 24 小时倒计时，也不需要知道后台随机轮换的具体时刻。

### 8.2 普通刷新

首次进入、每次进入或切回页面、购买成功后（入账完成）、资格净消耗变化后，服务器都重新校验当前状态。

未到期、仍达标、仍上线且未冷却的旧礼包优先保留。有空位时可以补充其他候选；候选不足时按数量规则缩减。

新达标或刚结束冷却的礼包可以进入候选池，但当已有展示有效且名额已满时，不强制替换已有礼包。**因获赠金币抵减而资格失效的现有礼包，即使24小时未到期也必须立即撤销。**

请求失败不是“没有礼包”。前端应显示获取失败或重试状态；未成功取得最新可售结果时，不可把旧缓存当成新的购买许可。

### 8.3 到期替换范围

多个礼包可能有不同到期时间。只有一部分礼包到期时，原则上只更新到期项，并保留其他仍有效项；不强制把整组全部重抽。

“优先未展示组合”是指相对于**本次刷新前的当前展示列表**，不是指用户历史上从未见过。曾在更早时间出现、但当前未显示的合格礼包可以再次参与分配。

填充空位时，先从刷新前未显示的可用候选中无放回抽取；数量不足时，再从其余合格旧组合中选择。正常候选无额外权重时等概率选取；如以后增加权重，需要单独配置和记录。

当展示目标不变、有到期位置且确实存在未显示的可用替代组合时，至少换入一个不同组合；可替换更多时尽量多换。没有替代组合时，不能虚构“至少换一个”的结果。

继续使用同一旧组合时，也必须创建新的展示授权，旧展示记录不能永久续用。

### 8.4 候选恰好 4 个时的 4 → 2

当前展示四个礼包、可用候选也恰好是这四个，且至少一个展示记录到期、无法从列表外引入新组合时，允许将本次展示缩减为两个。

缩减时优先保留仍未到期且剩余有效期较长的礼包。若未到期礼包超过两个，超出的礼包因数量规则隐藏；若需从已到期礼包中选择，则为选中项新建 24 小时展示记录。

服务器同时保存“缩减展示状态”，记录开始时间、结束时间和当前候选集合标识：

> 缩减状态结束时间 = 本次执行 4 → 2 的时间 + 24 小时。

只要状态尚未结束且可用候选集合没有实质变化，普通页面刷新仍以两个为目标数量，不能因为 N 仍等于 4 就立即补回四个。

缩减期间若某张卡片自己到期，可以在两张展示位内正常替换。单礼包到期不自动结束缩减状态。

缩减状态在以下任一条件发生后结束：到达其结束时间；可用候选身份或有效售卖配置发生实质变化，例如购买导致冷却、新门槛达标、冷却结束、礼包上下架或配置变化。结束后重新按正常数量规则处理。

候选集合保持四个且缩减状态到期时，可以恢复展示四个。恢复时保留仍有效的已有礼包，加入其他候选，不重置保留项的 24 小时有效期。

因此，相同条件下不会因连续刷新而立即出现“4 → 2 → 4 → 2”的来回切换；因真实资格变化或时间节点导致的变化则允许发生。

### 8.5 仅两个候选与其他边界

只有两个候选时，两个均到期可以继续显示相同商品，但后台为到期项创建新的展示记录。不为制造变化隐藏成一个。

用户长时间离线后，只需在再次请求时依据当前条件处理一次，不补演离线期间每一轮随机过程，也不把尚未结束的购买冷却当成展示到期清除。

### 8.6 同时到期示例

下表假设原展示同时到期、没有待确认支付、用户候选未变化，且未处于缩减展示状态。

| 当前候选 | 原展示 | 预期处理 |
|---:|---:|---|
| 23 | 4 | 换入另外四个 |
| 6 | 4 | 换入两个未显示礼包，另外两个从旧合格礼包中重新分配 |
| 5 | 4 | 换入一个未显示礼包，另外三个重新分配 |
| 4 | 4 | 缩减为两个，并记录缩减状态 |
| 3 | 2 | 换入一个未显示礼包，另一个重新分配 |
| 2 | 2 | 可以继续使用原两个商品，但更新已到期展示授权 |

## 九、下单、支付与履约

### 9.1 创建订单的校验

新建订单必须同时确认：当前登录用户、当前展示记录所属用户、稳定礼包身份、有效配置版本、未过期、**按最新 A－B－C 计算的资格净消耗仍达到门槛**、仍上线、未处于购买冷却、没有冲突订单或其他不可售限制。

用户必须购买自己当前展示记录中的商品。仅提交一个符合门槛的组合 ID，不构成购买许可；同样不能使用其他用户、旧设备页面或已经被替换的展示记录。

校验失败时返回礼包已更新或当前不可购买，并让前端刷新。服务器不能为了让请求成功，临时把用户请求的隐藏礼包分配给他，也不能自动替换成另一个价格或奖励的礼包并扣款。

币种、实付金额和金币奖励以服务器锁定内容为准，不能采纳客户端修改后的值。

判断授权有效并创建订单、消费本次下单机会，必须作为不能被并发重复通过的一次业务操作处理。同用户不同设备、不同支付入口和重复点击遵循同一份状态。

### 9.2 支付中锁定

默认同一用户在本活动同时最多一笔待确认支付订单。订单创建成功后，活动进入该用户的支付确认暂态。

前端保留最近一次礼包列表，所购礼包显示“支付处理中”，其他购买入口暂时禁用；切回页面或其他设备打开页面时，先展示同一订单状态，不新增随机购买授权。该暂态不作为正常的 0/2/4 可售结果。

支付过程中可以继续校验资格和时间，但不因普通刷新替换正在处理的订单或重新开放购买。等待结果期间的展示超时不修改订单创建时锁定的商品内容；支付成功后即使其他礼包因赠送抵减而失去资格，也不能据此否认这笔先前合法订单。

用户仅关闭收银台或客户端弹出取消，不等于服务器已确认订单取消。释放锁定以订单已成功，或已确认失败、取消、关闭且不能再按正常流程扣款为准。

### 9.3 支付成功

服务器核验合法订单付款人、金额、币种、支付结果和订单有效性后：

1. 只确认一次支付成功，记录首次确认成功时刻。
2. 使已购礼包的原展示授权失效，建立该用户对此礼包的 48 小时冷却。
3. 按创建订单时锁定的内容，在同一次入账里发放基础金币和额外赠送金币（记成两行）；每行只产生一次有效到账记录。
4. **入账成功时，仅将额外赠送这一行计入 C，重新计算资格净消耗**。基础充值金币不参与资格抵减，额外赠送不重复计入游戏获得 B。
5. 入账成功后解除支付锁定；先按新净消耗筛掉失效候选，再决定保留、缩减或补位，最终一次性返回 0/2/4 列表。
6. 若支付已成功但入账还没完成（钱包故障或超时），订单继续占着支付锁定，**不能新建其他订单**，不能先释放为可连续购买的正常可售状态；入账或异常处置完成后再刷新。
7. 前端收到最终列表后整体更新，不先在页面残留一个三卡或单卡的正常可售状态。

确认支付成功后，即使用户离开页面、礼包过期、因本单赠送抵减导致资格净消耗跌出门槛、礼包已经正常下架或页面改成两款，仍按合法有效订单完成履约，不重新套用新建订单的展示校验来拒绝发奖。

支付成功的记录、冷却限制和防重复履约需要保持一致。服务重试不能短暂重新开放同一礼包的购买权限，也不能把补发当成新交易。

### 9.4 失败、取消与超时

确认未成功支付的订单不发金币，也不生成 48 小时购买冷却。释放锁定后，依据当前时刻完整刷新；原礼包只有仍上线、达标、未冷却且重新具有有效展示记录时，才可以再次下单，不无条件恢复旧页面。

本地等待超时不等于支付失败。达到支付期限但结果未知时，进入“支付结果确认中”，进行核对或关闭订单，不能仅按计时器到点就放开另一笔购买。

### 9.5 延迟通知与异常扣款

以经核验的支付完成时间判断是否符合订单锁定的支付期限，而不是仅依据通知到达服务器的时间。

| 情况 | 处理 |
|---|---|
| 支付在有效期限内完成，通知延迟到达 | 正常确认并履约，按服务器首次确认成功时刻开始 48 小时冷却 |
| 支付结果尚不能确定 | 保持核对状态，不发奖、不误判失败，也不开放冲突订单 |
| 已确认未支付并关闭的订单收到异常扣款，或支付不符合有效期限 | 核对实际资金后进入异常收款退款流程，不直接丢弃通知 |
| 同一成功通知再次到达 | 返回已处理结果，不再次发奖、不重置冷却 |

## 十、服务端刷新处理顺序

每次需要返回新的正常可售列表时，按同一用户的当前状态串行确定一次结果：

1. 若存在待确认支付，先返回支付处理状态，按第九章处理，不发放新的购买授权。
2. 使用服务器当前时间汇总滚动窗口内有效游戏支出 A、游戏获得 B、已到账本活动额外赠送 C，计算资格净消耗 max(0, A−B−C)，再结合发布状态、48小时购买冷却和其他限制，形成当前去重候选池。已支付但入账未完成时，订单仍占着支付锁定，同样先返回支付处理状态。
3. 净消耗变化造成候选集合改变时，结束不再适用的缩减展示状态；确定本次目标为 0、2 或 4；满足四候选无替代的到期条件时，可新建缩减状态。
4. 移除已购、冷却、下架、**获赠后净消耗不足导致资格失效**、版本失效和到期的展示授权。保留不超过目标数量的仍有效旧项。
5. 如有空位，优先从本次刷新前未显示的候选中选择；不足时再选择其余合格候选，确保不重复。
6. 只为新选或重新分配的项目建立新的 24 小时展示记录；保留项的时钟不动。
7. 一次性保存最终列表、撤销旧授权和必要的状态原因，然后返回完整结果。

服务器作出的随机结果必须持久保存。同一时刻两个设备同时刷新，不得各生成一份互相独立的有效购买列表。

缓存只能辅助展示，不能成为下单授权来源。每次创建订单均需检查当前服务端状态。

## 十三、状态与移除原因

### 13.1 分层状态

| 对象 | 主要状态 |
|---|---|
| 组合配置 | 待选择、已发布、已下架 |
| 用户对此礼包的资格 | 净消耗未达标、可参与分配、购买冷却、入账未完成（占着支付锁定）、其他不可售限制 |

## 十四、经济规则与运营边界

### 14.1 48 小时冷却的实际约束

本方案只限制同一用户对同一礼包的重复购买，不限制用户连续购买不同组合。

例如用户在购买前满足 23 个不同组合，并不表示这 23 个可以依次全部购买。每购买成功一个礼包，本次额外赠送到账就会降低资格净消耗；**只有重新计算后仍达标、仍被分配且未冷却的其他礼包才可继续购买**。48 小时同礼包冷却不能被当成“整个活动每 48 小时只能购买一次”或“同一赠送档位每 48 小时只能领取一次”。

如果组合 A、B、C 使用同一个赠送档位，但支付价格或最终奖励不同，它们分别冷却；**如果每次赠送后资格净消耗仍达到该档门槛，并被服务器分配展示**，用户才可能分别购买并多次获得该赠送。

### 14.2 净消耗资格可重复判断，但额外赠送会降低资格

最近 N 天的**资格净消耗**可同时用于判断多个不同礼包，并不是一次购买就按礼包门槛扣除对应的消耗额度。但每笔本活动赠送到账，会作为收益进入 C，使资格净消耗下降；所以不能再说“购买不会影响资格”。

例如用户游戏净亏损（A−B）为 120,000，本活动尚无赠送；购买一个额外赠送 50,000 金币的礼包后，新的资格净消耗为 70,000。原来满足 100,000 门槛的其他礼包将立即失效；已经购入的那个礼包另进入 48 小时冷却。用户继续游戏产生新的有效净支出时，资格净消耗才可能重新上升。

实际金币收入可以短期抵消游戏支出；用户拿到赠送币后用来玩游戏，如果后续游戏产生有效扣款，A 仍随之增长，结算获得部分又记入 B。运营需要评估该循环的持续资格变化与赠送发币规模，不能把赠送抵减理解成永久扣除资格或全活动总赠送预算。

### 14.3 投放前的检查

后台应展示不同组合的单位价格金币数、额外赠送金币、同价更优组合、低价反而奖励更多等关系，供人工选择时核查。

上线前需要根据实际游戏回收能力评估单用户连续购买不同组合时可能获得的总赠送量。必要时另行配置全活动赠送预算、同赠送档位共享限制或其他明确上限。**这些上限与 A−B−C 的资格计算是不同规则，不可混为一谈。**

上述额外上限不在本方案中默认为已启用；若业务决定启用，必须明确统计周期、扣减及退回口径、超限后是否移出候选，以及合法已创建订单的预留处理，不能只在支付之后临时拒绝赠送。

## 十五、核心一致性要求

1. 候选按稳定礼包身份去重，当前列表最多四个且不能重复。
2. 正常可售列表只为 0、2、4，支付中及已支付待入账使用独立暂态。
3. 当前未分配的候选不能直接下单；旧展示授权不能被长期复用。
4. 同一用户同一礼包冷却期间不再授权购买，相同商品跨普通配置版本不能绕过冷却。
5. **资格净消耗统一按 max(0, A−B−C) 计算，且 A、B、C 使用同一滚动窗口。**
6. **仅本活动实际到账的额外赠送计入 C，基础充值金币不计入；同一份赠送不能同时计入 B 和 C，更不能因重试重复抵减。**
7. 赠送到账降低资格后，原有未到期但不再达标的礼包也必须立即撤销，重新按 0/2/4 展示；其消失不产生冷却。
8. 冷却只由正常支付成功触发，非购买隐藏不产生冷却；冷却到期不等于重新达标。
9. 冷却结束只解除限制，不保证达标、不保证展示，更不自动下单。
10. 重复刷新不无故重新抽取、不重置保留礼包的有效期、不重置购买冷却或重复扣除赠送。
11. 4 → 2 后保存缩减状态；相同时间和候选下，连续刷新结果稳定。
12. 待确认支付、已支付待入账的订单占着支付锁定，不允许创建冲突订单，也就不会基于未抵减的旧资格连续下单。
13. 已合法支付的有效订单按下单快照履约，支付期间因赠送抵减产生的资格变化不否认已创建的合法订单。
14. 重复成功通知不重复发奖，补发不变成第二次购买，冷却时间不因重试改变。
15. 游戏返还、赠送退款追回和历史流水滚出窗口，按原流水调整资格，不把相关金额永久扣除。
16. 发放金币、支付实收、订单快照、个人冷却、资格抵减流水及后台统计可以相互核对。

| 47 | A=200,000、B=80,000、C=30,000 | 资格净消耗 90,000，只满足不高于 90,000 的门槛 |
| 48 | A=100,000、B=120,000、C=5,000 | 资格净消耗按 0 计算，不允许使用负数作为资格 |
| 49 | 仅充值基础金币，没有游戏记录和额外赠送 | 基础金币不影响 A、B、C，净消耗保持不变 |
| 50 | 购买含额外赠送 50,000 的礼包前，资格净消耗为 120,000 | 赠送实际到账后净消耗变 70,000，原本 100,000 门槛的未购礼包立即失效 |
| 51 | 购买礼包后，由原有四个可售候选跌为仅两个 | 不强行补满四个，正常列表立即调整为两个 |
| 52 | 购买礼包后，由原有四个候选跌为仅一个 | 正常页面显示暂无礼包；没有购买过的其他礼包不进入冷却 |
| 53 | 同一额外赠送发奖通知重复三次 | C 只增加一次，冷却也不延长，余额不重复增加 |
| 54 | 本活动赠送先到账，用户后续用这笔金币参与有效游戏 | 赠送已在 C 抵减；后续真实游戏扣款才增加 A，游戏返还进入 B，不能把到账再当游戏扣款 |
| 55 | 游戏下注扣除 10,000，结算返还 8,000 | A 增加 10,000、B 增加 8,000，净消耗仅增加 2,000，不能重复减去返还 |
| 56 | 支付成功后一次入账 | 基础金币和额外赠送同一次进钱包，同一次提交里生成 C 流水，没有“赠送晚到”的空档 |
| 57 | 合法订单已创建，随后游戏中奖使用户跌出原门槛 | 有效付款按原订单快照履约；资格下降只阻止之后的新建订单 |
| 58 | 额外赠送记录滚出7天窗口，部分游戏支出仍留在窗口 | C 中对应记录移除，净消耗可能回升，按实时资格参与候选 |
| 59 | 已发放的额外赠送因退款被实际追回 | 对 C 做对应冲正并重算资格，不额外清除或重启48小时冷却 |
| 60 | 一份奖励被补发或后台重新同步 | 只补齐缺失的发奖记录；已经记过的抵减不能再次扣除 |
| 61 | 更改已发布同价同总奖励礼包中的基础/赠送拆分 | 仍共享原冷却身份，但新订单按新的基础/赠送快照计算资格抵减，不追改已付订单 |
| 62 | 游戏记录使用结算净亏损作为 A，同时再次减去返还 B | 属于重复扣减错误，验收必须拒绝此计算方式 |
| 63 | 用户买箱 500，开箱得到 700（含 500 本金） | 买箱计入 A，奖励到账计入 B，净消耗只因额外的 200 降低 |
| 64 | 宝箱过期后用户进入活动页，系统自动退款 500 | 退款到账计入 B，与买箱支出冲平，净消耗不变 |
| 65 | 宝箱奖励到账使某礼包刚好跌出门槛 | 该礼包展示授权立即撤销，不产生冷却 |
| 66 | 月卡奖励到账或金币购买月卡 | 不计入 A、B、C，资格净消耗不变 |

## 十七、生产配置待填内容

上线前仍需由运营提供各实际基础档位、完整赠送档位与**资格净消耗门槛**，以及人工选中的生产礼包列表。

示例中的 10,000 和 100,000 赠送档位尚未提供消耗门槛；缺失时不得发布。

如计划上线 100 个不同商品，需要足够的有效配对，并通过最终商品去重和人工发布。生产验证应同时覆盖 A−B−C 资格计算、游戏返还及额外赠送抵减、入账失败重试、重复记账和退款冲正，以及 24 小时展示、48 小时冷却、正常和异常支付、并发刷新。
