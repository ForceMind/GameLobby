# 游戏大厅活动与任务后端管理算法文档

> 修订：2026 年 10 月 21 日按评审结论修订：时区跟运营大区、净消耗口径统一（宝箱买箱算支出）、补月卡处理器、礼包冷却与展示对齐产品文档（见同目录 REVIEW.md）。

本文规定游戏大厅活动与任务的配置模型、周期计算、用户状态、条件判断、奖励结算和管理后台行为，供产品、后端、管理后台、客户端和测试共同实施。

系统采用统一的活动与任务引擎。运营通过活动 ID、任务 ID 和发布配置定义内容；服务器根据可信业务事件计算用户资格与进度，并通过可追踪的奖励订单完成发放。新增同类活动、调整条件阈值、奖励及时间，可以通过配置完成；新增尚未支持的玩法算法，需要扩展对应的服务端处理器。

产品规则的细节以各活动自己的产品文档为准：《明日宝箱产品功能需求说明书》《金币随机礼包活动产品需求文档》《游戏月卡功能需求说明书》。本文只写统一引擎的算法、数据和接口；两边对不上的时候，先改文档，再开发。

## 1 整体设计

### 1.1 活动与任务的关系

活动负责组织玩法、参与范围、有效时间、任务组合及公共限制。任务负责描述用户要完成的行为、进度计算方式和完成后的奖励。活动可以包含多个任务，也可以直接采用签到、转盘、宝箱、礼包等专用玩法处理器。

每日任务、每周任务、每月任务和一次性任务使用同一套任务模型。没有限时活动归属的常驻任务，挂在一个常驻任务活动下，不另建一套结算逻辑。

必须把任务的两个维度分别配置：`reset_type` 表示每日、每周、每月或一次性；`objective_type` 表示登录、有效游戏局数、胜利次数、累计投入、支付、邀请等目标行为。例如“每日完成 100 次有效旋转”同时具有 DAILY 和 GAME_ROUND_COUNT 两个属性。

### 1.2 核心对象

| 对象 | 标识 | 作用 |
| --- | --- | --- |
| 活动定义 | activity_id | 稳定的活动身份，保存活动名称和配置历史 |
| 任务定义 | task_id | 稳定的任务身份，描述目标行为及规则模板 |
| 活动任务绑定 | binding_id | 描述某任务在某活动中的位置、依赖及奖励范围 |
| 发布包 | release_id | 固定活动、任务、奖励、指标口径和玩法参数的确切版本 |
| 活动轮次 | activity_run_id | 某活动实际开放的一轮，例如某周的周末活动 |
| 用户活动实例 | user_activity_id | 某用户在某一轮活动中的参与记录 |
| 用户任务实例 | task_instance_id | 某用户在某次绑定、某个任务周期中的进度和权益 |
| 奖励订单 | reward_order_id | 一次应发奖励的冻结内容、发放状态及到账凭证 |

配置版本回答“按照哪套规则算”；活动轮次和任务周期回答“这是哪一次参与”；奖励订单回答“这次奖励是否已经到账”。三者必须分别保存。

### 1.3 默认运行约定

以下是本系统的初始设计默认值，均应在后台可见；允许调整的内容必须经过配置发布，不能由客户端临时覆盖。

| 项目 | 默认规则 |
| --- | --- |
| 业务时区 | 跟随用户所属的运营大区。大区与时区的映射来自运营中台；用户首次参与某轮活动、或建立任务实例时解析并固定，之后不随设备或大区变化；大区没有有效时区时，阻止新参与 |
| 日周月刷新 | 每日 00:00；每周一 00:00；每月 1 日 00:00 |
| 时间边界 | 有效区间统一为开始包含、结束不包含，即 [start, end) |
| 自动任务 | 用户无需打开任务页，可信事件可以自动建立实例并计数 |
| 触发当次行为 | 计入进度；需要排除的任务显式配置 |
| 普通任务历史回溯 | 不回溯到生效时间或触发时间之前 |
| 同一事件参加多个任务 | 默认允许；每个目标实例只计算一次 |
| 普通任务完成判定 | 达标锁定；只适用于普通累计行为 |
| 净消耗等动态指标 | 在配置指定时点取快照或重新校验，不默认首次达标永久锁定 |
| 普通任务领奖 | 手动领取；每个周期的每个奖励档位一次 |
| 普通任务迟到接收 | 进度截止后 24 小时内首次持久接收的有效事件可补算 |
| 普通任务领取尾期 | 进度截止后 48 小时；父活动同时提供足够领取尾期 |
| 一次性任务 | 默认用户在该 task_id 下终身一次；活动限定任务需显式修改范围 |
| 历史记录 | 不清零、不覆盖；按周期新增记录 |

上表就是默认配置档案 `LOBBY_V1`。发布时要把档案里的值展开写进发布包（见第 17.1 节），以后改档案不影响已发布的内容。

签到、转盘、明日宝箱、限时购买等即时行为使用各自的接收截止；例如当日签到和宝箱开启没有普通任务的 24 小时迟到点击宽限。

## 2 活动配置

### 2.1 基本信息与发布信息

| 字段 | 含义与要求 |
| --- | --- |
| activity_id | 必填，活动稳定唯一标识；不得通过名称识别活动 |
| activity_code | 运营可读编码，同环境内唯一 |
| name_i18n / description_i18n | 多语言名称、规则说明；支持英文默认内容 |
| activity_type | TASK_BUNDLE、SIGN_IN、WHEEL、CHEST、BONUS_OFFER、MONTH_CARD、COMPOSITE |
| handler_key / handler_version | 对应服务端玩法处理器及兼容版本 |
| tenant_id / app_id / environment | 租户、应用和环境隔离范围，服务端鉴权确定 |
| config_version / release_id | 草稿版本与实际发布包；保存草稿不改变线上版本 |
| owner / tags / sort_order | 负责人、标签、显示顺序 |
| display_config | 图标、横幅、入口、跳转位置、多语言资源引用。语种范围固定 10 种：English（默认）、简体中文、繁體中文、हिन्दी、Bahasa Indonesia、ไทย、Tiếng Việt、Español、Português (Brasil)、العربية；阿拉伯语从右向左排版 |
| publish_state | DRAFT、IN_REVIEW、APPROVED、PUBLISHED、ARCHIVED |
| effective_at | 发布包允许开始应用的时刻，不得追溯影响已经结算的历史 |

ID 本身不携带类型或日期语义。页面名称、图片和排序变化不会生成新的业务身份。

### 2.2 时间与循环

| 字段 | 含义与要求 |
| --- | --- |
| timezone_source | 固定为 REGION：时区取自用户所属运营大区。排期里写的本地起止时间，发布时按每个启用的大区展开成各自的轮次 |
| region_id / timezone | 用户实例上保存解析出的大区和 IANA 时区，创建后不可随设备或大区变化 |
| preview_start_at | 预告展示时间；允许早于活动开始，不允许参与 |
| enrollment_start_at / enrollment_end_at | 可加入活动的总时间范围 |
| hard_end_at | 所有参与者最迟停止累计和新操作的时间；长期活动可为空 |
| recurrence_type | NONE、DAILY、WEEKLY、MONTHLY、FIXED_INTERVAL |
| recurrence_rule | 每 N 个周期、指定星期、月日期、开场时间等结构化规则 |
| recurrence_anchor_at | 循环锚点；固定时长循环必须配置 |
| occurrence_duration | 每轮持续时长，区别于两轮之间的间隔 |
| max_occurrences | 最大轮数，可为空；总起止范围仍然约束轮次 |
| start_mode | GLOBAL 或 USER_RELATIVE |
| user_anchor_type | FIRST_ELIGIBLE_EVENT、REGISTERED_AT、FIRST_LOGIN 等可信起点 |
| user_duration | 个人活动持续时长；必须声明自然日或经过时长 |
| late_accept_duration | 截止后接收业务事件的补算宽限，不延长用户实际操作时间 |
| claim_grace_duration | 本轮进度结束后仍可领取已达成奖励的时间 |
| hard_claim_end_at | 全部历史轮次最迟允许新领取的时间，可为空 |
| expiry_policy | 未完成过期；已完成未领取过期、自动发放或转待领邮箱等明确策略 |

面向运营的“活动开始时间、结束时间”必须映射到上述字段。全局活动通常入场结束与累计结束一致；新用户七日活动必须同时显示“最后加入时间”和“最迟结束时间”，避免晚加入用户拿不到完整七天。

### 2.3 资格与参与控制

| 字段 | 含义与要求 |
| --- | --- |
| audience_rule | 国家、渠道、平台、等级、注册时间、用户分组等参与范围 |
| visibility_rule | 是否显示入口；入口可见不代表可参与或可领奖 |
| trigger_rule | 建立用户活动实例的条件，如首次有效游戏、登录或点击加入 |
| participation_limit | 每用户每轮、每日、终身允许参与的次数及明确范围 |
| cooldown_rule | 冷却对象、范围、起算事件和时长；不同活动不能隐式混用 |
| exclusion_group | 互斥活动组及确定的选择优先级；仅对声明互斥的活动生效 |
| assignment_rule | 分组、灰度或实验分配规则；固定入场分组，规则版本按具体实例和周期固定 |
| participation_cost | 金币、道具、次数或支付订单；成功与失败时的扣减规则 |
| entry_validity | 资格取得后何时失效，是否可跨日、是否消耗资格凭证 |
| complete_rule | 活动整体完成条件，可为空；不影响没有终局目标的持续活动 |
| activity_reward | 活动总奖励；必须与任务奖励分开定义，防止多发一份 |
| budget_policy / stock_policy | 奖励预算、奖品库存及预留方式 |
| runtime_control | 运行、暂停、停止参与、暂停发奖等即时控制及原因 |

活动整体完成可按“指定任务全部完成”“完成任意 N 个任务”“累计活跃度达到目标”配置。引用任务时要明确使用 COMPLETE 还是 GRANTED 状态，以及统计哪个任务周期。任务活跃度使用唯一完成记录增加，消息重试不能重复加分。

## 3 任务与绑定配置

### 3.1 任务核心字段

| 字段 | 含义与要求 |
| --- | --- |
| task_id / task_code | 稳定任务标识与运营编码 |
| name_i18n / description_i18n | 展示文案与规则；展示的目标和奖励来自生效配置 |
| objective_type | LOGIN、GAME_ROUND_COUNT、WIN_COUNT、GAME_SPEND、PAYMENT、INVITE、CUSTOM_METRIC 等 |
| reset_type | DAILY、WEEKLY、MONTHLY、ONCE；扩展 FIXED_INTERVAL 需声明锚点 |
| reset_timezone / reset_at | 周期时区和刷新时刻，默认继承用户所属大区的时区 |
| week_start / month_day | 周开始日和月刷新日；月刷新日默认只能选择 1 日 |
| activation_mode | AUTO 或 MANUAL_ACCEPT；手动接取任务要有接取接口 |
| trigger_rule | 什么行为或状态使任务开始累计 |
| trigger_event_included | 触发任务的本次事件是否也贡献进度，默认 true |
| progress_start_mode | FROM_ACTIVATION、CURRENT_PERIOD、LIFETIME；后两者属于显式历史回溯 |
| progress_window | CURRENT_TASK_PERIOD、SINCE_ACTIVATION、ROLLING_DURATION 等统计窗口 |
| metric_rules | 指标、事件筛选、聚合方法、去重字段、统计单位 |
| complete_rule | 指标目标及 ALL、ANY 组合逻辑 |
| completion_mode | LATCH、AT_CLAIM、AT_PERIOD_END、SNAPSHOT_ON_ACTION |
| task_validity | 接取后的个人有效时长；与活动、任务周期取交集 |
| once_scope | USER_LIFETIME、ACTIVITY_LIFETIME、ACTIVITY_RUN；ONCE 时必填 |
| repeat_limit / overflow_policy | 首期普通任务固定 1 次且不跨周期结转；重复任务须由明确处理器扩展 |
| claim_mode / claim_grace_duration | MANUAL 或 AUTO；领取尾期，不得模糊继承 |
| reward_set_id / reward_tiers | 奖励内容、阶段阈值和每档领取次数 |
| correction_policy | 业务撤销或纠正后的未领奖回退、已发奖处理规则 |

“每日任务”和“统计最近七天消耗”可以同时存在：前者决定一天创建几个任务实例，后者决定读取哪些数据。不得用一个 cycle 字段同时表达这两个概念。

`progress_start_mode` 控制能否读取激活前事实，`progress_window` 定义实际统计窗口。滚动窗口若允许读取活动开始前七天，必须配置允许该历史范围；二者冲突时禁止发布。历史查询不会补建过去各期奖励权益。

### 3.2 活动与任务绑定字段

| 字段 | 含义与要求 |
| --- | --- |
| binding_id / activity_id / task_id | 绑定身份及两端引用；发布包固定 task_version |
| enabled / visible / sort_order | 是否启用、是否展示及排序 |
| binding_start_at / binding_end_at | 在活动内的开放时间，不能突破父活动累计范围 |
| prerequisite_rule | 前置任务或前置奖励状态，禁止循环依赖 |
| progress_scope | 默认 BINDING 独立进度；明确要求共享时使用共享组 |
| progress_group_id | 共享进度组；指标、时间范围、触发和版本必须兼容 |
| reward_scope / reward_group_id | 独立发奖或共享同一份奖励；与共享进度分别配置 |
| activity_points | 完成该任务贡献的活动活跃度 |
| override_fields | 允许覆盖的阈值、奖励或文案白名单；最终值进入发布包快照 |

同一任务模板可以用于多个活动，但默认生成不同进度。共享进度不自动意味着共享奖励。对 USER_LIFETIME 一次性任务，即使出现在多个活动中，也由同一个终身权益键防止重复领取。

## 4 标识与唯一性算法

业务唯一性必须在持久化数据库中保证，客户端按钮置灰和缓存锁只负责体验或削峰。以 PostgreSQL 为例，组合唯一约束可以保证多列组合不重复；去重键各字段应为非空，避免 NULL 的默认比较语义造成漏洞。[1]

### 4.1 活动轮次与用户实例

```text
namespace = tenant_id + app_id + environment
run_key = (namespace, activity_id, region_id, schedule_identity, occurrence_start)
user_activity_key = (namespace, user_id, activity_run_id, participation_index)
task_instance_key = (namespace, user_id, binding_id,
                     user_activity_id, task_period_key, repeat_index)
```

以上是结构化元组，实际可使用数据库联合列或无歧义编码后的哈希。不能直接无分隔拼接字符串。`schedule_identity` 表示稳定排期身份，普通改文案、阈值或奖励不改变它；变更排期只影响未来轮次，禁止凭修改版本制造重叠新轮次。

每日展示键可用 `2026-10-19`，每周用该业务周的开始日期，每月用 `2026-10`。实际 task_period_key 使用稳定 period_definition_id 与真实 UTC 周期起点生成，同时保存任务范围、时区和周期起止；单独日期不是完整业务身份。

### 4.2 奖励权益与领取键

```text
普通任务 benefit_scope = binding_id + user_activity_id + task_period_key
终身一次 benefit_scope = task_id + USER_LIFETIME
活动内终身一次 benefit_scope = activity_id + task_id + ACTIVITY_LIFETIME
每轮一次 benefit_scope = activity_run_id + task_id + ACTIVITY_RUN
共享奖励 benefit_scope = reward_group_id + 明确的共享周期范围

benefit_key = (namespace, user_id, benefit_scope, tier_id, repeat_index)
reward_entitlement 唯一约束 = benefit_key
reward_order 唯一约束 = benefit_key
wallet_credit 唯一约束 = (namespace, reward_order_id, reward_item_id)
```

`config_version`、`release_id`、客户端随机请求号不参与权益身份。新版本、跨端点击和换一个请求号重试，均不能使同一权益变成新奖励。若确实要给用户再领一次，必须配置新的业务任务或新的明确轮次，不能靠版本号重置。

`tier_id` 是稳定逻辑档位，复制发布包时不得重建。ONCE 任务的 repeat_limit 必须为 1，repeat_index 固定为 0；调整原档金额不新增权益。新增档位或新的业务任务属于显式新增权益，发布预览必须显示会影响哪些既有用户。

## 5 时间与周期计算算法

### 5.1 时间基准与边界

持久时间使用 UTC 时间戳；运营排期和自然日边界按照用户所属大区的时区计算。所有关键时间来自服务器、业务数据库或可信网关。客户端传来的时间只可作为诊断信息。

在 `[start, end)` 规则下，00:00:00 恰好发生的事件属于新的一天。每周依据业务周开始日期计算，跨年时不能简单使用“自然年 + 周数”拼接。每月从本月 1 日到下月 1 日，不能把月固定为 30 天。

支持夏令时市场时，自然日按当地日历计算，不固定增加 86400 秒。首版只开放安全的刷新日期选项；遇到某地区不存在或重复的本地刷新时刻，排期发布必须显示解析后的 UTC 时刻，并固定“缺失时刻顺延到首个有效时刻、重复时刻取第一次”的产品规则及时间库版本。不得交给各客户端自行推断。

### 5.2 固定间隔与日历循环

```text
固定间隔循环：
  要求 interval > 0，occurrence_duration > 0
  默认 occurrence_duration <= interval
  n = floor((time - anchor) / interval)
  要求 n >= 0；存在 max_occurrences 时 n < max_occurrences
  run_start = anchor + n * interval
  run_end = min(run_start + occurrence_duration, hard_end_at)
  只有 run_start <= time < run_end 才在本轮开放时段内

日历循环：
  先在该大区的时区按日历规则生成本轮开始
  再计算对应的结束并转换为 UTC
  应用总入场范围、例外日期和 hard_end_at 的裁剪
```

固定间隔公式只适用于经过时长，例如每 48 小时一次。每天 00:00、每周五 18:00等需求必须走日历算法。默认禁止同一活动开放时段相互重叠；开放结束后的领奖尾期可以与下一轮并存，接口必须按轮次分别返回。

### 5.3 个人活动

个人活动的锚点保存一次，例如首次符合条件的服务端事件时间。用户退出、跨设备登录或重新安装不能重设锚点。

```text
user_start = 可信锚点，且满足入场总时间范围
user_end = min(按 user_duration 计算的个人截止, hard_end_at)
user_claim_end = min(user_end + claim_grace, hard_claim_end_at)
```

无硬截止的字段按无限远处理。自然日七天是“锚点所在业务日到第八天 00:00”；经过时长七天是“锚点后 168 小时”，两者必须分别命名。要保证完整七日参与，需使最后入场时间与硬截止相隔足够时长，发布校验必须验证该承诺。

USER_RELATIVE 活动的轮次入场结束只约束新参与者，不截断已加入用户的个人时长。此类轮次的 enrollment_end 与用户累计截止分别存储，不能将前者冒充后者参与后续最小值计算。

### 5.4 任务有效区间

```text
effective_start = max(活动轮次开始, 用户活动开始,
                      绑定开始, 任务周期开始, 规则允许的进度起点)
effective_end = min(适用的全局累计硬截止, 用户活动结束,
                    绑定结束, 任务周期结束, 接取后有效期截止)
late_accept_end = effective_end + late_accept_duration
claim_end = min(effective_end + claim_grace_duration,
                用户活动领取截止, 活动硬领取截止)
```

区间为空时不生成可执行任务。普通任务配置需满足 `late_accept_end < claim_end`；父级领取尾期不能把它裁剪成不合法配置。即时玩法设置迟到宽限为零，使用自己的操作截止。

GLOBAL 的全局累计硬截止包含本轮累计结束；USER_RELATIVE 忽略轮次入场关闭，只受个人截止和明确的 hard_end_at 约束。JOIN 还需在总入场区间内；处理历史合法行为不能因为当前已停止入场就拒绝补算。

上述有效区间约束触发、普通逐事件累计和可执行动作。显式历史回溯、终身指标和滚动统计使用自己独立的 metric_window 与历史下界，可以按已发布规则读取活动开始或用户加入之前的事实。

跨周期采用新增实例，不清零历史记录。旧周期可领奖时，返回“本期任务”和“往期可领”两组记录，不能用同一个任务卡片覆盖旧权益。

### 5.5 迟到与关账

按事件的可信业务发生时间归属周期；按活动事件网关的首次持久接收时间判断是否在补算宽限内。消费线程实际执行时间不决定迟到资格。事件网关需在活动判断前可靠落库，队列重复投递保留原首次接收时间。

任务周期结束后进入 SETTLING，停止接收本周期新发生的行为，但接收允许范围内的延迟事件。超过接收宽限的事件进入纠错队列，不算到新周期，也不悄悄丢弃。

结算工作必须等待已及时接收的相关事件处理完毕及数据水位满足要求。若系统积压跨越领取截止，记录 SETTLEMENT_BLOCKED；恢复后给受影响的尚未发放权益设置 `max(原领取截止, 恢复可领取时间 + 24小时)` 的故障补偿截止，并形成可审计记录。正常业务过期不自动延长，已发奖记录不重新开放。

## 6 条件引擎

### 6.1 条件职责

| 条件类别 | 回答的问题 | 判定时点 |
| --- | --- | --- |
| 展示条件 | 用户是否看到入口或锁定任务 | 页面查询时 |
| 参与条件 | 用户是否属于允许参加的人群 | 入场时；静态分组保存快照 |
| 触发条件 | 何时建立用户活动或任务实例 | 对应可信事件或接取请求时 |
| 进度筛选 | 哪些业务事件计入哪些指标 | 每次事件处理时 |
| 完成条件 | 指标是否达到目标 | 按 completion_mode 规定的时点 |
| 领取条件 | 当前是否允许创建发奖订单 | 点击领取或自动领取时 |
| 即时拦截 | 暂停、已过期、账号限制等是否阻止本操作 | 每次关键操作时 |

静态分组快照不意味着忽略后续即时拦截。已经赚取的普通任务奖励，不因用户等级升高、分组改变或入口隐藏而自动丢失。

### 6.2 结构化规则

每个原子条件必须有 `condition_id`、数据来源、指标、筛选项、聚合方式、统计窗口、比较符、目标值和单位。ALL 表示全部满足，ANY 表示任意满足；允许有限层级嵌套。首版限制嵌套 5 层、原子条件 50 个，超限发布失败。

可用比较符为 EQ、NE、GT、GTE、LT、LTE、IN、BETWEEN；BETWEEN 明确含两端。可用聚合为 COUNT、SUM、MAX、LATEST、COUNT_DISTINCT、STREAK。NOT 仅允许用于即时状态或已关闭窗口，不能对尚未到齐事件的“没有发生”提前发奖。

```json
{
  "logic": "ALL",
  "conditions": [
    {
      "condition_id": "rounds",
      "metric": "valid_round_count",
      "event_type": "game.round_settled",
      "filters": {"game_group": "slot", "is_valid": true},
      "aggregate": "COUNT_DISTINCT",
      "distinct_by": ["game_id", "round_id"],
      "window": "CURRENT_TASK_PERIOD",
      "operator": "GTE",
      "target": "100",
      "unit": "round"
    }
  ]
}
```

条件只引用注册过的事件字段与指标；后台不能上传任意 SQL、JavaScript 或无限循环表达式。纯配置未覆盖的新指标，先由后端注册取数、聚合、纠错与成本约束，再允许运营使用。

### 6.3 指标口径

| 指标 | 必须明确的业务口径 |
| --- | --- |
| 有效游戏局数 | 服务端最终结算成功；无效局、取消局、重复回调不计 |
| 有效投入金币 | 只读游戏投入流水；充值、转账、宝箱购买不自动属于游戏投入 |
| 净消耗金币 | 按指定指标口径聚合游戏投入与收益抵减，见第 9 节 |
| 支付金额 | 支付平台验证成功后的金额；使用最小货币单位并限定币种 |
| 邀请人数 | 被邀请用户满足定义的激活条件；按被邀请用户 ID 精确去重 |
| 连续签到天数 | 按业务日排序，不按事件到达顺序累计；缺日后的处理明确配置 |
| 累计登录天数 | 一个业务日最多贡献一天；不等于登录次数 |
| 在线时长 | 可信会话区间并集，重叠设备和断线重连不能重复计时 |

金额和金币使用整数最小单位、64 位安全范围或更高精度整数存储，不使用浮点数做权益运算。对 JavaScript 客户端，可能超出安全整数范围的 ID、金币累计值和金额以十进制字符串返回。不同币种禁止未经汇率快照直接相加。

### 6.4 完成方式

LATCH 用于有效游戏次数等普通累计任务：达标后记录完成时间与证据快照，之后发奖产生的收益不会让任务退回未完成。业务撤销和作弊纠正依然按纠错策略处理。

AT_CLAIM 用于余额、最近七天净消耗等动态条件：展示为“当前满足”，点击时重新读取一致快照；不足则不能创建新奖励订单。奖励订单一旦合法创建，使用该快照继续发放，不被自己的到账结果反向撤销。

任务进入领取尾期后，目标指标的统计截至时刻不能超过 effective_end，不能把结束后的新游戏计入旧任务；账号限制等即时领取条件仍按当前状态检查。必须实时读取当前动态资格的礼包等专用玩法，使用自己的操作截止，不借普通任务尾期继续获取新资格。

AT_PERIOD_END 用于必须在周期终局判断的条件：接收宽限结束、数据水位完整后统一冻结结果。SNAPSHOT_ON_ACTION 用于购买资格、宝箱开奖等：在该业务动作接受时保存指标快照与选择结果。

普通累计指标也不能逐事件随意覆盖；COUNT_DISTINCT 必须维护唯一事实，撤销时相应减少。MAX、LATEST、STREAK 在原事实被纠正时可能要重算，不能统一用一个 progress 加减字段实现全部聚合。

## 7 状态管理

### 7.1 活动状态

活动发布状态、时间阶段和运营控制分别存储。草稿不是一种运行中的活动阶段；暂停也不能覆盖掉实际已经到期的事实。

| 时间阶段 | 行为 |
| --- | --- |
| UPCOMING | 可按预告规则展示，禁止新参与及进度累计 |
| OPEN | 在有效区间内，允许满足条件的参与、累计与领取 |
| SETTLING | 新行为截止，处理迟到事件；普通已完成任务可领，终局判定任务等待结算 |
| CLAIM_ONLY | 进度已结算，仅允许领取已有权益 |
| CLOSED | 不接受新领取；已受理的发奖、退款和纠错继续完成 |

常驻活动可以持续 OPEN，其中的每日任务分别进入各自的结算和领奖阶段。整体完成条件为真时记录用户级 `completed_at`；是否阻止后续任务需由活动 `stop_on_complete` 明确配置，默认只锁定活动总奖励。

个人活动关闭入场后，已参加用户仍按自己的有效区间累计；不能因入口关闭就让所有用户同时进入 CLAIM_ONLY。

### 7.2 用户任务与奖励状态

用户任务分别保存 task_phase 和 progress_status。时间阶段 task_phase 使用 OPEN、SETTLING、CLAIM_ONLY、CLOSED；完成状态 progress_status 使用 LOCKED、IN_PROGRESS、COMPLETE、EXPIRED、REVIEW_REQUIRED。每个奖励档位独立使用 LOCKED、CLAIMABLE、PROCESSING、GRANTED、EXPIRED、REVIEW_REQUIRED。任务完成与奖励到账不共用一个 completed 字段。

任务达到 5 局可有第一档奖励，达到 10 局可有第二档奖励；每档有自己的权益键。阶段奖励默认每档分别领取，不会领取高档后再次补发已经发过的低档。可配置 INCREMENTAL 累计领取或 HIGHEST_ONLY 只领最高档，两种方式的资源预算不同，发布时必须选择。

HIGHEST_ONLY 首期只在周期结算完成后确定最高档，不提前领取低档；以任务范围和 repeat_index 建立独立于 tier_id 的 tier_choice_key，跨档只能选中一份权益。需要先领低档、后来补差额时使用另外明确的差额奖励处理器，不能套用 HIGHEST_ONLY。

INCREMENTAL 中每档配置数量表示该档新增奖励。例如两档分别填 100 和 200，总共可得 300，不把 200 当作累计总额。共享奖励权益的各入口必须引用同一冻结条款和资源预留，不能各自承诺不同金额却只在最后领取时竞争。

AT_CLAIM 动态任务在订单受理前可以从“当前可领”变回“不满足”；已受理订单进入 PROCESSING 后使用冻结快照。钱包尚未确认到账时，客户端不得显示 GRANTED。

奖励订单和奖励行有自己的状态，和上面的权益档位状态分开：

| 对象 | 状态 |
| --- | --- |
| reward_order | CREATED（已受理）、PROCESSING、PARTIAL_PROCESSING、GRANTED、CANCELLED、REVIEW_REQUIRED |
| reward_item | PENDING、SUCCEEDED、UNKNOWN、FAILED_RETRYABLE、FAILED_FINAL |

流转：奖励行从 PENDING 出发，到 SUCCEEDED、UNKNOWN、FAILED_RETRYABLE（回到 PENDING 重试）或 FAILED_FINAL；UNKNOWN 查单后变成 SUCCEEDED 或 FAILED_*。所有奖励行都 SUCCEEDED，订单才是 GRANTED；有成功也有未完成的是 PARTIAL_PROCESSING。只有确认没有任何资产被执行过，FAILED_FINAL 的订单才能 CANCELLED 并释放资源。

### 7.3 暂停和下线

运营控制至少包含以下独立开关：`block_new_entry`、`block_progress`、`block_new_claims`、`block_reward_dispatch`。普通暂停默认只禁止新参与，已有用户继续累计和领取；其他控制需明确选择并填写原因。

暂停进度时保存暂停时间区间，按照业务事件发生时间判断。暂停前发生、暂停后到达的合法事件仍可处理。暂停发奖只影响尚未发送的订单；已经发出且结果未知的订单必须继续核对，不能假定其未到账。

暂停默认不顺延排期。需要延长时，建立针对明确轮次或受影响用户的时间调整记录，保留原截止、调整原因、操作者和新截止；不改已结束历史的原始配置。

## 8 事件处理算法

### 8.1 可信事件契约

游戏结算、支付到账、钱包入账、邀请激活和签到等，由对应服务端产生事件。客户端不能直接提交“任务已完成”“奖励 1500 金币”或可信进度增量。

| 字段 | 作用 |
| --- | --- |
| event_id / producer | 传输事件唯一标识和签发服务 |
| schema_version / event_type | 事件结构版本和类型 |
| namespace / user_id | 环境、应用及用户范围 |
| business_id / business_revision | 局号、支付单号或流水号，以及该事实的修订版本 |
| occurred_at | 可信业务发生时间，例如游戏结算时间 |
| first_received_at | 活动网关第一次持久接收时间 |
| producer_sequence / ledger_cursor | 对有顺序要求的数据记录源序号或账本水位 |
| game_id / order_id / currency | 相关对象与币种，按事件类型要求 |
| payload | 有效性、投入、总返还、数量等白名单业务字段 |
| original_business_id | 撤销或修正时引用原业务事实 |

同一局可能先发送“结果产生”，再发送“钱包结算完成”。发布规则明确选择最终可信事件及业务去重键，例如 `(game_id, round_id)`，不能把两条消息当成两局。重复业务回调更换 event_id 也应被业务事实键识别。

### 8.2 候选规则匹配

发布时生成 `event_type → game_id/game_group → 候选任务或活动规则` 索引。事件到达后只检查相关候选，再过滤环境、用户范围、有效时间和条件。

候选索引必须保留仍在迟到接收期或尚未完成最终结算的历史轮次。无需对每条游戏事件扫描所有活动，也无需午夜对全体用户执行批量清零。后台工作器负责预热轮次、关闭窗口和补偿，实际有效性仍可通过固定配置和服务器时间重新计算。

### 8.3 处理流程

```text
receive(event):
  验证生产者、环境、结构和业务字段
  持久化 inbox，唯一键为 (namespace, producer, event_id)
  已存在则返回原接收记录，不更新时间
  成功持久化后确认接收

process(event):
  更新或读取规范化事实；旧修订不覆盖新事实
  重复修订仍检查未完成的目标分发，不能提前整体返回
  candidates = 当前及可补算规则匹配目标
               并集 该事实历史已贡献目标 并集 未完成分发目标
  持久化本事实修订的目标分发清单和待处理记录
  for each candidate:
    已有实例读固定版本；新实例按周期起点和固定分组选择版本
    用 occurred_at 定位轮次、任务周期和暂停区间
    校验首次接收时间、资格、触发条件和前置关系
    必要时幂等建立用户实例，保存业务激活时间
    开启单目标事务：
      锁定目标进度；读取该事实旧贡献及 applied_revision
      锁内重读最新事实，仅应用高于该目标已应用的修订
      计算新修订的贡献，按新旧差额或重算更新指标
      保存贡献记录，唯一到目标、指标和业务事实
      按 completion_mode 判断并保存完成证据
      为新达成的档位幂等建立奖励权益
      若自动领取，写入待受理领取事件
      保存该目标处理完成记录及 outbox
    提交
  仅在所有目标均完成或明确无贡献后标记本事件分发完成
```

如果处理完任务 A 后在任务 B 前崩溃，重试时 A 的贡献不会重复，B 仍会继续处理。不能只用一个全局“event 已消费”标记挡掉所有后续目标。

修订可能使原来有效的游戏变成无效，或改变业务时间和目标归属。必须反查历史贡献目标并撤销旧贡献，再为新目标计算；仅匹配修订后的事件索引会遗漏原任务的扣减。目标级 applied_revision 在锁内单调增加，避免较旧消费者晚执行时回退新结果。

针对已有贡献的正式撤销不受普通迟到接收截止或历史索引退场限制，转入独立纠错流程。它可以更正原权益，但不能借纠错为其他已经过期周期补建无关的新奖励。

自动实例的 `activated_at` 是业务规则确定的激活时间，不是数据库插入时间。迟到的触发事件到达后，应补放已经接收、且本来属于有效区间的后续事实；这是故障补算，不等于允许运营未声明的业务历史回溯。

COUNT、SUM 更新保留未封顶原始值，页面进度条可以封顶。共享累计指标、多个奖励档位和撤销重算都依赖原始值。精确领奖门槛不使用可能产生误差的近似去重计数。

### 8.4 原事实撤销

撤销通过新事件引用原事实，不物理删除历史。尚未受理发奖的权益重新校验，必要时撤回；PROCESSING、UNKNOWN 或部分到账订单先核对或受控取消，不能视为“还未到账所以可直接撤回”。已发奖记录保持可追溯，创建独立纠正单，根据配置选择扣回、挂账或人工复核。

纠正不能仅按当前生效配置重算历史，要使用原实例保存的版本、窗口与口径。普通后续赢钱和活动赠币造成净消耗下降，与“原交易作废”是不同情况，不能走同一撤奖分支。

## 9 金币流水与净消耗算法

### 9.1 统一指标口径

净消耗以实际发生的业务流水计算，不用当前钱包余额减初始余额。每笔流水记录资产类型、金额、互斥业务分类、原业务单、实际入账时间和可追踪的指标时间。

设置 `metric_policy_id` 固定统计口径：游戏范围、统计窗口、奖励来源集合、流水时间口径和撤销规则。大厅默认口径是 `lobby_net_consumption_v1`，明日宝箱和金币随机礼包的资格共用它：

- 支出 = 有效游戏投入 + 宝箱买箱。
- 获得 = 游戏总返还 + 宝箱奖励 + 宝箱过期退款 + 礼包额外赠送。
- 其他签到、任务、转盘赠币和月卡的收支默认不计入。要计入某个来源，必须显式加进来源集合，并检查对应的支出是否也要一起计入，保持两边对称。

| 流水类别 | 钱包变化示例 | 净消耗贡献 |
| --- | --- | --- |
| GAME_BET 有效游戏投入 | 减少 X | +X |
| GAME_PAYOUT 游戏总返还 | 增加 X | -X |
| PACK_PAID_BASE 礼包付费基础金币 | 增加 X | 0 |
| PACK_BONUS 礼包额外赠送 | 增加 X | -X |
| CHEST_REWARD 已领取宝箱总奖励 | 增加 X | -X |
| CHEST_PURCHASE 宝箱购买本金 | 减少 500 | +500（计入支出；算这只宝箱自己的奖励时不计它自己的买箱） |
| CHEST_PRINCIPAL_REFUND 过期点击退款 | 增加 500 | -500（计入获得，冲平买箱支出） |
| 已计算但未发放的宝箱奖励 | 无变化 | 0 |
| 其他活动奖励（签到、转盘、任务等） | 增加 X | 默认 0；要计入必须加进 metric_policy 的来源集合 |
| MONTH_CARD_PURCHASE_COIN 金币购月卡 | 减少 X | 0 |
| MONTH_CARD_REWARD 月卡奖励 | 增加 X | 0（月卡不参与净消耗） |
| 交易撤销 | 原交易的相反变化 | 按原分类和原贡献做对应修正 |

宝箱已领取的总奖励全部计入获得，包括奖励里加回去的 500 本金；买箱的 500 计入支出，两边抵消，对净消耗真正有影响的只有奖励里的额外部分。宝箱过期不开时，买箱的 500 留在支出里，用户点击退款后退回的 500 计入获得，把它冲平。付费礼包必须拆成基础金币和额外赠币两行，避免基础购买金币被错误抵减。

### 9.2 计算公式

```text
N = sum(窗口内有效游戏投入)
    + sum(窗口内宝箱买箱，不含正在算奖励的那只宝箱自己的)
    - sum(窗口内游戏结算总返还)
    - sum(窗口内指定来源已实际到账的奖励金币：宝箱奖励、宝箱过期退款、礼包额外赠送)
    + sum(归属于该窗口的有符号修正)

net_consumption = max(0, N)
```

`payout_amount` 表示游戏返还总额，如果包含投入本金，就完整纳入总返还。如果游戏服务只有净差额 `net_delta = payout_amount - bet_amount`，使用等价的 `-net_delta`；不能先算净差额再扣一遍派奖。

本公式的账务默认采用“原始已入账贡献加追加冲正”路径：原流水不因被撤销而从求和中删除，再由关联的逆向贡献抵消。若某个读模型已经提供重述后的最新有效净值，就不再叠加同一修正。事实贡献修订和账本追加冲正是两条等价取数路径，禁止同时使用而重复修正。

同一钱包流水只选入一次，即使同时带有“获得金币”和“活动奖励”标签，也不能重复抵减。先保留带符号的 N 并完整求和，最后在展示与门槛比较时截零；不能逐笔、逐日截零，也不能使用历史最大净消耗。

例如最近七天游戏投入 100000、宝箱买箱 500、游戏总返还 70000、已领宝箱奖励 3000（含 500 本金）、礼包额外赠送 2000，则当前净消耗为 100000 + 500 − 70000 − 3000 − 2000 = 25500。购买得到的 60000 基础金币不改变该值；再发 5000 赠币到账后，后续净消耗变为 20500。

### 9.3 快照与并发

每次使用动态净消耗决定资格或奖励，保存 `metric_policy_id`、窗口起止、`as_of`、各来源账本水位、原始 N、截零结果及输入分类汇总。统计窗口统一用明确的开始包含、结束不包含规则；取数截止必须处于本次读取之前已完成的可信业务提交之后，同时间精度的交易通过源序号明确先后。

顺序固定为：读取发奖前完整快照 → 接受本次权益或购买 → 冻结本次奖励 → 实际入账 → 更新后续净消耗。不能把本次尚未入账的奖励先减掉再重新抽奖，形成循环计算。

页面可以读缓存，购买和领取必须使用权威状态。若赠币刚到账而统计聚合尚未追上，下一笔受同一资格口径约束的补贴操作应等待该水位、回源补齐或返回处理中。按 `user_id + eligibility_group_id` 协调冲突操作；读模型过期时不能继续使用旧消耗连续购买多个礼包。

对配置为互相冲突的操作组，还需持久化 inflight 占位：从本次资格快照被接受开始，到钱包结果确认且指标追上对应水位后才释放。短事务结束不释放该占位，UNKNOWN 不按普通 TTL 清除。这样可同时封住“订单已受理未到账”和“已到账但聚合未更新”两个窗口。

净消耗仍是统计指标，不自动变成每次购买要扣除的积分额度。不同任务能否共同基于同一段消费发奖，属于明确的奖励叠加规则；锁机制只保证先后顺序和数据一致。

### 9.4 时间窗口与冲正

默认过去七天指动作发生时刻之前的滚动 168 小时；需要“前七个完整自然日”时使用另一种窗口枚举。流水移出窗口时，即使用户没有新事件，动态资格也可能变化，查询和关键动作必须重新计算或刷新到正确水位。

实际新奖励按实际入账时间贡献；正式撤销原流水时，保存真实撤销时间，同时按原贡献的指标时间重述原窗口。不能把七天前的赠币追回伪装成今天新的游戏亏损。每次历史快照保留当时可见的数据水位，以便解释更正前后差异。

## 10 奖励配置与抽取算法

### 10.1 奖励内容

| 字段 | 含义 |
| --- | --- |
| reward_set_id / version | 奖励组及配置版本，由发布包固定 |
| reward_mode | FIXED、RANDOM_WEIGHTED、RANDOM_RANGE、TIERED |
| reward_item_id | 稳定奖励行身份，跨重试保持不变 |
| asset_type / asset_id | 金币、宝石、道具、抽奖次数、资格券或权益 |
| quantity / min / max | 固定数量或范围，使用整数最小单位 |
| weight | 加权抽取的非负整数权重 |
| reward_source | 钱包记账来源分类，决定净消耗等指标如何使用 |
| issue_mode | 自动或手动；与任务奖励档位绑定 |
| asset_expiry | 道具或权益有效期；与奖励领取截止分开 |
| budget_scope / stock_scope | 预算和库存所属活动、轮次及资产 |
| reservation_mode | GUARANTEED_ON_ENTRY 或 LIMITED_AT_CLAIM |
| snapshot_timing | 在参与、完成、操作受理或周期结算时冻结 |

固定组合奖励如 1500 金币加 3 宝石，建立一个权益和两条奖励明细。展示的奖励范围与实际执行配置同源；客户端只执行表现动画，不决定奖品和数额。

### 10.2 加权随机

```text
W = sum(weight[i])，要求 W > 0
r = 服务端安全随机生成 [0, W) 内的无偏整数
按固定顺序累计权重
选择首个 cumulative_weight > r 的奖项
持久化 (benefit_key, reward_set_version, result, input_snapshot)
```

范围随机必须声明是否均匀，整数上下限都包含；非均匀分布使用注册过的算法版本，不用模糊的“随机”字段。使用安全随机 API 提供的无偏区间采样，不能直接对不整除的随机整数取模。

正式随机结果针对每个权益只保存一份；并发时由唯一约束决定唯一正式结果。网络重试、服务重启、配置发布、领取延迟和预算不足都不能重抽。结果尚未正式保存时不可返回给客户端。

### 10.3 预算与库存

默认有上限且承诺保证奖励的活动使用 GUARANTEED_ON_ENTRY：在接受用户参与、每日任务激活或收费操作之前，预留承诺范围内最大可能需要的资源。阶段奖励分别可领时预留各档总额；随机金币预留最大数额，正式抽取后缩减为实际数额。

库存型奖品若无法对每个可能抽中的奖品提供保证，应采用事先声明的库存奖池：奖池版本、可抽库存集合、选中结果与扣减在一次受控原子操作内确定。运营不得在抽到大奖后因库存不足偷偷改奖或重抽。

LIMITED_AT_CLAIM 仅适用于产品明确展示“限量、先领先得”的场景。资源不够时返回明确的无库存状态，不标记发放成功，也不消耗用户应保留的付费资产。免费参与名额耗尽与已承诺奖励欠发必须区分。

GUARANTEED_ON_ENTRY 的资源不够时：自动激活的任务（例如每日任务）当期不建立用户任务实例，记录原因 BUDGET_EXHAUSTED 并告警；需要用户主动参与的玩法，参与接口返回 OUT_OF_STOCK，不扣费、不建立参与记录。已经建立的实例和已受理的订单不受影响。

预算分别维护已预留、已发放、已释放；同一资源使用条件更新或行锁原子校验。承诺生效前保证最大资源，正式随机结果在配置指定的完成、开启或结算时点保存一次。共享权益只预留一份；旧周期的预留仍归旧周期账目，不因新周期开始而清零。PROCESSING 或钱包 UNKNOWN 的订单不因普通 TTL 到期释放资源，防止到账后预算又被别人使用。

每项预留唯一到 benefit_key 与 resource_slot，保存具体 budget_account_id 或 stock_account_id、资产、所属轮次和预算周期。领取、缩减、支出及释放始终引用原 reservation_id，不按领取当天重新选预算账户。循环任务只预留本期已接受的明确义务，不在首次入场时无限预留未来各期。

## 11 奖励发放与幂等算法

### 11.1 两层幂等

请求幂等键由客户端提供，用于识别同一次网络请求；业务权益键由服务器根据用户、任务实例、周期和档位生成，用于保证业务上最多一份奖励。同一个请求键携带不同参数返回冲突；不同请求键指向同一权益返回同一订单。

订单范围必须包含用户和环境，不能让某用户猜到他人的 task_instance_id 后领取。客户端传来 task_id 只能定位配置，不能直接据此结算。

### 11.2 本地事务与发放工作器

```text
claim(user, task_instance_id, tier_id, request_key):
  鉴权并定位本人实例
  若 benefit_key 已有订单：返回该订单当前结果
  transaction:
    锁定权益；检查周期、档位、数量限制及即时运营控制
    再检查该权益是否已有订单；有则返回原订单
    要求 server_now < claim_end 且权益允许首次受理
    LATCH 必须有有效完成证据；AT_CLAIM 必须本次校验满足
    按实例快照判断；AT_CLAIM 读取完整动态指标快照
    确认资源预留；必要时按声明的限量策略预留
    冻结奖励明细与唯一随机结果
    创建 reward_order 和各 reward_item
    将权益标为 PROCESSING
    写入 outbox 发放意图
  commit
  返回订单 ID 和当前状态

dispatch(order):
  按每条 reward_item 的稳定业务键请求钱包或背包
  成功回执：记录交易 ID，将该行标为 SUCCEEDED
  超时/响应不明：标为 UNKNOWN，按原业务键查询或重试
  明确未执行且可重试：重试原订单的原奖励行
  所有行均确认成功：订单 GRANTED，权益 GRANTED
```

在同一数据库内，权益、奖励订单、预算预留和 outbox 必须同事务提交。如果钱包账本也在同一事务边界内，可直接原子入账；跨服务发奖采用事务 outbox 和接收方幂等，避免数据库成功而消息丢失。outbox 仍可能重复投递，因此钱包端同样需要业务唯一键。[2]

事务锁定多个对象时使用固定顺序，并为冲突事务做有界重试。不得先改用户余额，再尝试记录领取状态。

### 11.3 未知、失败与多资产

钱包超时不表示未到账。UNKNOWN 订单保留原业务键、预算与库存预留，继续查单；即使超过重试次数，也只进入待核对队列，不创建新的补发单冒险重复入账。

多资产由同一钱包支持原子批量发放时优先使用批量；涉及多个服务时逐行记录。金币已成功、道具未确认，只重试道具，订单保持 PARTIAL_PROCESSING，不能把金币再次发一遍，也不能宣称全部到账。

领取截止约束的是首次合法受理时间。截止前已持久化受理的订单继续发完；截止后重试返回原订单，不能新建权益，也不能把已受理订单判过期。

明确不可恢复且确认没有任何资产执行时，才可按策略取消并释放资源。任何一行结果未知或部分到账，都必须先核对，再进行补发或退款处理。

### 11.4 参与成本与退款

消耗金币、次数、道具或支付的操作使用独立 `participation_order_id`，把费用、权益、随机结果和退款关联起来。同一业务动作不能并发扣两次费，也不能支付未确认就发两次奖。

同钱包费用与奖品可原子处理时优先合并；跨服务时先持久化操作并预留资源，再按稳定业务键确认费用，确认成功后交付奖励。费用状态未知时不允许换新单再次扣款。

取消与发放相互竞争时，由持久状态条件更新决定唯一分支。已经确定取消并退款的操作不能被晚到工作器再次发奖；结果未知时不先退款再期待自动纠正。退款建立独立退款单并引用原扣款，累计退款不得超过原已确认扣款。

## 12 具体活动接入规则

### 12.1 日周月及一次性任务

| 示例 | 周期 | 目标与发放 |
| --- | --- | --- |
| 累计旋转 100 次 | 每日 | 有效 slot 局精确去重累计；完成可领 1500 金币和 3 宝石 |
| 本周登录 5 天 | 每周 | 按业务日期去重，不把同日多次登录算多天 |
| 本月完成 200 局 | 每月 | 按自然月建立实例；奖励由对应档位配置 |
| 首次完成有效游戏 | 用户终身一次 | ONCE 加 USER_LIFETIME；活动换版后不能重新领取 |
| 本轮完成任意 3 个任务 | 每轮活动 | 活动总目标，使用任务完成权益去重累计 |

活动在一天中途开始或结束时，任务有效区间按交集裁剪，目标默认不按剩余时间折算。若产品只接受完整周期，设置 `partial_period_policy=SKIP`；默认 `ALLOW_WITH_FULL_TARGET`，后台排期预览必须显示首尾短周期。

### 12.2 签到

签到采用 SIGN_IN 处理器，配置签到周期天数、每天奖励、自然日序号、漏签规则和最终奖励附加条件。初始方案使用自然日发放、大奖固定最后一天、不支持补签。

以七日活动为例，CALENDAR_DAY 模式按本轮或个人活动开始日计算第 1 至第 7 天，错过某一天则该天过期；不能靠多次点击一天拿两天奖励。CONSECUTIVE 连续签到和 ACCUMULATED 累计签到是另外的模式，不能与自然日序号混用。

最后一天默认按当日签到领取该档奖励；如果要求前六天全部签到，则显式增加 `final_reward_condition`，同时在活动规则中显示。签到动作在服务端合法受理后建立当日唯一记录和奖励订单，发放失败重试原订单，不重新签到、不重新计算第几天。

### 12.3 幸运转盘

WHEEL 处理器初始固定 8 个奖项位置。每格绑定奖品和整数概率单位，若以万分比配置则各格之和必须等于 10000；所有格不能同时为零，奖品引用和库存策略必须有效。

用户每次抽奖产生独立的抽奖操作单。验证参与资格与次数 → 预留费用及奖励资源 → 按固定发布包抽取并保存唯一结果 → 确认费用 → 返回结果并发奖。动画异常、退出重进和请求重试都展示同一结果。

需要累计 N 次保底时，增加独立用户保底计数，明确作用范围与重置事件；保底判定、正式结果和计数变更必须放在同一受控操作中。未配置保底时没有隐式保底。

### 12.4 明日宝箱

CHEST 处理器使用独立宝箱实例，不能只用普通任务的 COMPLETE 状态表达“已购买、待开启、过期可退款”。配置包含购买价、资格事件、次日开启规则、开奖算法版本、开启截止和退款方式。

业务流程为：完成一次符合条件的游戏取得资格 → 使用 500 金币购买 → 次日 00:00（用户所属大区的时区）起可开启 → 当天结束前开启并领取 → 到期未领取转为可点击退款。服务器到期只计算并保存一次真实奖励结果，不将它发到钱包；用户上线点击后才退 500 本金。

正常开启在有效时间内受理并冻结奖励；过期计算按逻辑过期时刻的统计截止取数，延迟执行不能使用几天后的当前净消耗。开奖结果一经保存，不因用户重试、后台补跑或后来点击退款而重算。若数据水位未完整，保留待结算状态，补齐后完成同一次结算。

开奖记录与发奖记录分开：过期记录可保存“当时本可得到的奖励”，但只有实际到账流水才计入获得。正常已领宝箱的总奖励全部计入获得；买箱的 500 计入支出；过期后用户点击退款退回的 500 计入获得，与买箱冲平。

算某只宝箱自己的奖励时，窗口内排除这只宝箱自己的买箱流水（它自己的奖励也还没到账）；其他宝箱的买箱、奖励、过期退款都正常计入。礼包的额外赠送计入宝箱的获得，宝箱的买箱、奖励、过期退款也计入礼包的资格净消耗，两边用同一个 metric_policy。

宝箱范围、净消耗上限裁剪和概率参数由 `reward_algorithm_key` 及参数快照绑定到 CHEST 处理器。参数校验必须覆盖净消耗为零、上限低于配置下限和金额取整等分支。百分比参数必须定义其对分布的具体作用，不允许只填“50%”而未指定算法含义就发布。

领取完成后必须再发生一笔新的有效游戏才能获得下一次资格，不能重用购买前的游戏记录。默认一个用户同时最多一个未完成宝箱流程；退款结束后也要求新的游戏行为再激活，此项作为明确可调整的资格配置。过期、开启和退款竞争时，通过实例行锁与终局状态保证只进入一种结算分支。

### 12.5 金币礼包

BONUS_OFFER 处理器将基础付费礼包、额外赠送档位、净消耗门槛、用户展示列表和个人冷却分别保存。礼包商品使用稳定 `offer_combo_id`，由（支付币种、支付金额、最终到账奖励内容）推导，和基础档位、赠送档位怎么拆、内容版本、排序、文案都无关；改这些都不能绕过该用户的冷却。

展示以礼包产品文档第七、八、十章为准：正常只展示 0、2、4 个；候选之间等概率抽取；每次展示授权有效 24 小时、各自独立计时；候选恰好 4 个且有展示到期时缩成 2 个并保存缩减状态（最长 24 小时）；用户只能购买自己当前展示记录里的商品。后端为此保存 `offer_display_grant`（用户、offer_combo_id、配置版本、分配时间、到期时间、失效原因）和 `offer_display_state`（缩减状态的起止和候选集合标识）。算法细节本文不重复。

点击购买时重新验证资格、价格版本和展示快照，再建立支付订单。合法订单保存购买前的资格和赠币快照；该订单自己的赠币到账后不会使其失效。同资格组存在未确认付款或未完成赠币结算时，冲突的新购买等待原流程与指标水位确认，防止反复使用同一份过期资格快照。

支付服务确认成功后，同一组合进入该用户的 48 小时冷却池：

```text
cooldown_key = (namespace, user_id, offer_combo_id)
先按支付订单确认成功事件做业务幂等
cooldown_until = max(已有截止, 本单 confirmed_at + 48小时)
可再次购买条件 = server_now >= cooldown_until
```

冷却从服务器首次确认支付成功的时间（confirmed_at）开始；渠道返回的支付完成时间 paid_at 另存，只用来判断订单是否在有效期内。响应丢失或赠币延迟不能绕过冷却。购买失败且明确未扣款不进入冷却；支付状态未知时保留处理中占位。退款后默认保留原冷却，避免退款立即重复购买；需要例外时走有记录的独立规则。

支付成功处理标记与冷却更新同事务提交。旧订单回调重放不能覆盖或缩短后一次购买产生的新冷却，也不能按回调到达时间重新延长原订单的冷却。

基础付费金币与额外赠送金币分别入账，只有赠送部分抵减净消耗。赠币到账后重算该用户后续候选列表，已不满足门槛的其他礼包可以失去购买资格；已经合法受理的本次订单保持冻结内容。

支付回调晚到时，按平台验证的实际成功时间与订单有效期判断。有效期内已成功的支付，即使回调延迟仍履行原单；有效期后才成功的扣款，走该原单的取消退款策略，不能同时发奖。无法确认支付状态前，不能把占位当作普通缓存过期后直接清除。

### 12.6 月卡

MONTH_CARD 处理器按《游戏月卡功能需求说明书》实现，这里只写它和统一引擎的接口。

- 配置：一个月卡类型（商品组）下可以有多套配置。每套有适用大区、平台、渠道、人群，允许新开通的起止时间，金币价格，现金商品信息，以及奖励表（一张 31 天兜底表，加 28、29、30、31 天各一张）。配置发布后不可改，改动建新版本。同一用户同一时刻必须只命中一套配置；冲突禁止发布，运行中出现冲突则停止新下单。
- 期（card_period）：每次付款成功，或原生续费成功，形成一期。保存配置 ID 和版本、付款方式、订单、大区与时区、开通时间、到期日期、一期天数，以及选中的奖励表快照。到期日期是开通日期加 1 个月（没有同一号取当月最后一天）的 00:00；原生订阅以商店返回的到期时间为准，续费日锚定第一次订阅的日期。
- 每日奖励：第 1 天开通时自动发；第 2 天起每天 00:00 开放，用户手动领；每期每天只能领一次，漏领不补发。权益键是 (card_period_id, day_index)，走第 4.2 节的 benefit_key、第 11 节的奖励订单和发放流程。
- 付款：原生订阅、充值或第三方、金币的降级顺序，由服务端按渠道真实状态判断。订单支付期限不晚于配置允许开通的结束时间。金币购买用 participation_order（第 11.4 节）关联扣费和开卡，扣费成功但开卡失败必须补开或退回原扣除金币。
- 重复购买：有效期内同一商品组不允许手动叠购；两条渠道都付款成功时保留两笔记录，进入重复购买退款处理。
- 净消耗：月卡奖励和金币购卡都不进 metric_policy（见第 9.1 节）。
- 退款和撤销：按月卡文档第十一节处理；撤销后停止未发的奖励，旧的成功通知再次到达不能恢复权益。

以下是逻辑实体，不要求首期拆成同样数量的服务。可在同一后端和关系数据库中按边界实现，之后再按负载拆分。

| 逻辑表 | 关键内容与约束 |

| task_instance | 用户、绑定、周期、目标快照、进度、完成证据、截止 |

| admin_audit / runtime_control | 发布、审核、暂停、补发、时间调整及操作者 |

### 13.1 必要唯一约束

至少覆盖活动轮次键、用户参与键、任务实例键、权益键、钱包奖励行键、事件接收键和业务事实键。对同一事实的贡献使用 `(namespace, aggregate_target_id, metric_id, business_fact_id)` 唯一约束，修订在同一贡献身份下更新，防止同一事实多个修订相加。

COUNT_DISTINCT 还需要按指标去重对象保存精确贡献归属或引用数，防止多个事实指向同一被邀请用户时重复计数。取消一个事实不能把另一仍有效的事实一并删除。

### 13.2 查询索引

常用索引包括用户待领权益、用户本期任务、轮次与阶段、到期任务、未完成奖励订单、outbox 重试时刻、冷却截止、事实到贡献的反查和账本时间窗口。钱包与奖励对账按业务键，不靠文本描述匹配。

缓存可以保存生效 manifest、候选规则索引和列表读模型；必须带 release_id 与数据水位。缓存丢失后应可从数据库和账本重建，不能成为领取记录或唯一资格的唯一保存位置。

### 13.3 保留与归档

明细事件保留期要覆盖最大业务回溯窗口、迟到宽限及纠错期限；窗口结束后的聚合和证据可归档。终身一次性权益及防重凭证不能随普通事件日志清理，否则老用户会重新获得资格。

归档保留每份奖励的发布包、资格输入、结果、原订单和资产交易引用。已发布历史支持查询和导出，不支持直接修改目标、概率、奖品和已经结算的进度。

## 14 管理后台与发布算法

### 14.1 编辑页面

活动详情分为基本信息、时间排期、参与资格、任务配置、玩法参数、奖励资源、发布预览、运行记录八组。任务编辑页分别显示任务周期、目标类型、进度口径、触发与完成条件、奖励档位和领取方式，避免一个“任务类型”字段承担全部含义。

详情页同时展示生效版本、草稿版本及差异。任务、签到和转盘子页面可以独立编辑，但正式发布必须组成同一个发布包。仅仅保存活动外壳，不能让新概率与旧预算、旧任务目标同时在线。

### 14.2 发布校验

| 校验组 | 必须阻止发布的问题 |
| --- | --- |
| 身份与范围 | 缺少 ID、跨环境引用、未知处理器、资产不存在 |
| 时间 | 起止倒置、无效时区、非法重叠、空有效区间、领取早于补算截止 |
| 个人排期 | 宣称完整七日但最后入场者被硬截止裁短 |
| 条件 | 未注册指标、单位冲突、非法比较、过深规则或循环依赖 |
| 一次性与复用 | once_scope 缺失、共享组口径不兼容、重复奖励语义未选择 |
| 奖励 | 数量非法、概率不合法、范围上下限倒置、预算或库存预留不成立 |
| 版本 | 活动壳与任务或玩法参数不是同一个完整快照 |
| 历史 | 试图覆盖已经产生进度或结算的历史配置 |
| 数据能力 | 选择历史回溯但没有所需数据或无法完成可信快照 |
| 展示 | 目标、奖品、币种、时间或领取条件与实际配置不一致 |

发布预览应按每个启用的大区，展示至少未来三个轮次的开始、累计截止、补算截止和领取截止，以及模拟用户是否可进入、首个事件贡献多少、完成后会发哪些奖励。礼包预览包含赠币到账前后的净消耗变化和 48 小时冷却。

### 14.3 原子发布

```text
保存草稿时：按 draft_revision 做乐观并发检查
发布时：
  完成所有引用与业务校验，生成排期和用户样例模拟结果
  将活动、绑定、任务、奖励、指标和处理器参数展开为不可变 manifest
  保存 manifest_hash、审批记录和计划生效边界
  预建并验证新规则索引
  用 expected_current_release 原子更新生效发布指针
  发出配置变更事件；节点按 release_id 加载整份配置
  旧索引在旧实例补算和结算完成后按需退场
```

并发编辑冲突返回差异，不能后保存者无提示覆盖前者。发布切换只在完整配置可用后生效，不能让客户端分别缓存互不兼容的活动和奖励版本。

### 14.4 生效边界与灰度

限时循环活动默认从下一活动轮次应用新发布包。常驻任务中心默认按每个任务的下一自然周期应用新版本：每日任务明日切换，每周任务下周切换，每月任务下月切换；当前已存在实例继续用旧版本。后台必须逐项显示实际切换时间（每个大区各一份），不能把一个“已发布”误解为所有用户当前实例立即改变。

因此，常驻活动的 user_activity 记录保存参与身份及入场分组；每个 task_instance 另存自己创建周期的确切 release_id，不强制永远沿用第一次登录时的版本。任务依赖或跨任务共享组要求同步变化时，按共同边界整体发布，不把不兼容规则拼接到同一共享范围。

尚未物化的任务也按照业务周期起点选择版本，而不是按插入记录或消费消息时的最新版本。用户周三首次打开任务页，不会使该周任务擅自采用周三刚发布、原定下周生效的配置。新任务或新绑定中途首次开放时，按其明确的首个有效起点和短周期策略处理。

已上线绑定的 reset_type、时区和刷新锚点不允许作为普通阈值改版直接变更。需要调整周期定义时，建立新的稳定周期定义和绑定或明确迁移方案，并处理旧周期尾期及一次性权益范围；发布版本仍不参与权益去重。

限时活动同一期做灰度时，只允许周期身份、时区、累计截止与领取规则兼容的版本共存；用户首次参加该期时固定所属 release_id，换设备或扩大灰度比例不会换规则。常驻任务中心按每个任务周期固定规则版本，沿用前述周期边界。已经进入的用户不会同时生成两个灰度轮次。

同一期中途调整名称和图片等纯展示项可以走单独允许的展示发布；目标、奖励、概率、指标和时间等业务变更默认不热改。确需修复时，生成明确的实例迁移或补偿作业，先列出受影响实例、进度映射和奖励差额，再执行并记录结果。

回滚视为一次新的发布，按同样的未来活动轮次或任务周期边界生效。当前周期尚未物化的实例仍使用该周期起点适用的版本，不因创建早晚分裂规则。回滚不删除新版本下已有的任务进度、权益和钱包流水，也不释放仍在发放中的订单资源。

### 14.5 权限与环境

管理端区分查看、编辑草稿、审核发布、控制运行和执行补偿权限。预算、概率、奖励及金币口径变更保留审核轨迹；自动化服务只能在授权范围内发布或执行作业。所有写操作记录操作者、时间、对象、前后值、理由和请求标识。

测试、预发、生产的配置、子模块、事件、实例、库存、预算、奖励订单和钱包路由必须贯通隔离。环境由服务端身份与路由验证，客户端传一个 production 字符串不能取得生产权限。复制活动到生产只复制配置，重新映射奖品资源并校验，不复制测试用户进度或资金流水。

列表只计算和返回状态，不应因刷新页面触发扣款、抽奖、签到或发奖。允许幂等物化已成立的自动任务记录，但不能把“查看页面”暗中当成某个付费或领取动作。

### 15.2 响应字段

任务响应至少包含 activity_id、run_id、task_id、binding_id、task_instance_id、release_id、period_start、period_end、server_now、状态、各指标原始进度与目标、各奖励档位、claim_deadline、can_claim、disabled_reason、reward_order_id 和 data_updated_at。

客户端倒计时使用服务端时间偏差修正；最终是否接受操作仍由服务器判断。JSON 中的目标值、金额和累计金币使用约定的十进制字符串，客户端不得自行根据显示进度推算发奖数额。

常见业务码包括 NOT_STARTED、NOT_ELIGIBLE、NOT_TRIGGERED、PREREQUISITE_UNMET、NOT_COMPLETE、EXPIRED、COOLDOWN_ACTIVE、LIMIT_REACHED、OUT_OF_STOCK、PAUSED、CONFIG_CHANGED、PROCESSING、IDEMPOTENCY_CONFLICT。已领取请求返回原成功订单；不能统一当作失败引导用户重新创建领取。

### 15.3 管理与内部接口

管理接口覆盖创建草稿、编辑、复制、查看差异、校验、模拟、提交审核、审批、发布、暂停、恢复、归档、查用户进度、查奖励订单和发起纠错作业。编辑和发布使用期望版本检查，保留审计。

内部接口接收可信业务事件、查询账本快照与水位、预留资源、按业务键发奖和查单。它们仅向经过认证的服务身份开放，不暴露为任意客户端可调用的“增加进度”接口。

## 16 运行与对账

监控至少覆盖事件接收与消费延迟、未完成目标分发、迟到补算数量、权益形成数量、奖励受理与成功数量、UNKNOWN 和部分成功订单、预算已预留与已发放、库存不足、冷却拦截和各节点配置版本。

业务漏斗分别统计活动曝光、符合资格、实际参加、任务激活、完成、领取受理和实际到账。按用户去重的人数与按任务或订单计数的次数分列，不能直接互相相减当作流失。

对账按 reward_order_id 和 reward_item_id 关联权益、订单、钱包及预算：订单成功却没有资产凭证、资产已到账但订单仍处理中、同一权益多个资产业务键、预算释放但订单仍未知，都必须形成异常记录。修复以原业务键查询和补齐状态为先，不能直接给余额再加一遍。

配置发布和到期处理均可重试；系统重启根据数据库中的待处理记录恢复。运维调度负责推进关闭、过期计算、消息投递和对账，周期有效性及防重不依赖某一次调度恰好成功。

### 17.2 跨天事件与领取

用户在 10 月 20 日 23:59:58 完成第 100 局，事件于 10 月 21 日 00:00:04 首次进入活动网关。服务器将其记到 10 月 20 日实例，因为业务发生时间在旧周期内，首次接收也在允许补算范围内。

该实例的正常领取截止为 10 月 23 日 00:00。用户 10 月 21 日领取时，引用 10 月 20 日 task_instance_id；10 月 21 日的新周期可按触发规则独立产生新实例。重复投递第 100 局事件不会增加到 101，重复点击领取返回同一个奖励订单。

### 17.3 赠币影响礼包资格

假设礼包 A 要求最近七天净消耗至少 25000，购买前快照为 26000，赠送 5000 金币。合法订单先冻结该资格和赠币数量；入账后后续净消耗变成 21000。

## 19 实施顺序与完成标准

### 19.1 核心闭环

先实现稳定 ID、发布包、日周月及一次性实例、可信事件 COUNT 和 SUM、有效游戏局按业务事实键精确去重的 COUNT_DISTINCT、固定奖励、保证奖励所需的原子预留与原周期引用、请求与业务幂等、钱包查单、用户查询和草稿发布。此阶段即可交付每日旋转任务，并通过重复事件、跨天和重复领取验收。

### 19.2 指标与活动扩展

随后扩展其他精确聚合、连续日期指标、历史和滚动窗口、净消耗流水口径、动态资格、复杂库存与预留策略、冷却、签到与八格转盘，再接入明日宝箱和金币礼包处理器。每个处理器都必须使用同一套权益、订单、流水和审计约束。

### 19.3 运营与恢复能力

上线前完成同快照发布、运行控制、历史只读、环境隔离、超时查单、积压恢复、库存竞争和全链路对账。灰度、共享进度、最高档奖励和高级重复任务在对应算法与验收具备后开放配置项；后台不能展示可选但服务端没有正确实现的能力。

完成标准是：通过配置创建至少一个每日、每周、每月和终身一次任务，能够独立触发、累计、完成、领取、跨期与过期；任意重复事件或领取重试不多发，任意已受理奖励不会因重启或超时无记录丢失；每次发放都能追溯到固定规则和业务证据。
