# 游戏月卡功能需求说明书

> 修订：2026 年 10 月 21 日按评审结论修订：所有付款方式统一按自然月，奖励表按一期实际天数配置，时区跟运营大区，月卡不参与净消耗（见同目录 REVIEW.md）。

## 一 功能定位与规则边界

游戏月卡（对外名称“奖励月卡”）是游戏大厅中的持续权益活动。用户完成付款后立即开通，在权益有效期间按运营地区的自然日期获得每日奖励。

支付顺序为：优先原生订阅；原生订阅明确失败或不可用时，提供充值购买或第三方支付；这些方式全部明确失败或不可用时，最后提供金币付款。充值购买、第三方支付和金币付款均为单次购买，到期后需要用户手动再次付款。

运营可以同时维护多套月卡配置。每套配置包含适用范围、允许新开通的时间、付款信息及奖励表（按一期的实际天数配置，见 4.2）；每一期用户月卡必须明确绑定一套配置及其版本。后台既能从用户查询当前生效的配置，也能从配置查询当前生效的人数和用户名单。

### 1.1 本文采用的补充默认规则

下列规则用于补齐原始需求，属于本方案提出的默认口径：

| 项目 | 补充默认规则 |
| --- | --- |
| 一期的长度 | 所有付款方式统一按自然月：开通当天计为第1天，到期日是开通日加1个月的同一号（没有同一号取当月最后一天），到期日00:00失效，一期28到31天 |
| 领取方式 | 首日奖励随开通自动发放，第2天起到最后一天由用户当天手动领取 |
| 漏领处理 | 用户个人漏领不补发、不顺延；系统故障导致的漏发另行补偿 |
| 重复购买 | 本期有效期间不允许手动叠购同类型月卡；到期后可重新购买 |
| 配置变更 | 当前已购周期保持购买时承诺的奖励，不受运营修改影响 |
| 自动续费的配置 | 默认沿用该订阅已经约定的奖励版本；手动重新购买匹配当时可售配置 |
| 金币统计 | 月卡不参与净消耗：奖励金币不算获得，金币购卡也不算支出 |
| 时区 | 所有时间都跟用户所属运营大区的时区走，开通时定下，一期内不变 |

### 1.2 本文定下的两处边界

**第一处是一期的长度。** 月卡不再固定30天，所有付款方式（原生订阅、充值购买、第三方支付、金币）统一按自然月：开通当天算第1天，到期日是开通日加1个月的同一号，没有同一号就取当月最后一天，到期日00:00失效。所以一期是28到31天，奖励天数跟这一期的实际天数走，奖励表怎么配见4.2。

**第二处是原生订阅。** Apple、Google的自动续费订阅本来就按自然月续，和上面的规则一致，不需要另设30天：Apple按原购买的日历日期续费，没有这一天就取当月最后一天，之后回到原来的日期；Google的标准周期里有“每月”，没有任意30天。一期的起止以商店返回的到期时间为准，不自己推算。[Apple官方订阅期限说明](https://developer.apple.com/help/app-store-connect/reference/in-app-purchases-and-subscriptions/auto-renewable-subscription-information/)；[Google Play官方基本方案说明](https://support.google.com/googleplay/android-developer/answer/140504?hl=en)。Google“每月”遇到月末的处理，官方页面没写明，接入时要用测试账号核对。

## 二 时间与运营地区

### 2.1 月卡有效期

1. 以服务端核实的真实支付成功时间作为本期生效时间；核实后立即建立权益，不等第二天。通知延迟的情况按第五节补齐权益和系统造成的漏发。
2. 开通当天计为第1天，当天剩余时间长短不影响日序号。
3. 第2天起随绑定运营时区的日期变化而推进。
4. 到期日00:00失效，到期时刻本身不再属于有效期。
5. 按当地日历加1个月计算到期日期（没有同一号取当月最后一天），不按固定天数或秒数计算。
6. 不因用户未登录、未领奖而暂停或延长。

统一表达：

> 到期日期 = 开通日期加1个月；没有同一号取当月最后一天。到期时间 = 到期日期在本期运营时区中的00:00。  
> 有效区间 = 开通时间（包含）至到期时间（不包含）。一期天数 = 到期日期减开通日期。

例如用户所属大区的时区是Asia/Shanghai，于2026年10月21日15:00开通：

| 项目 | 时间 |
| --- | --- |
| 开通及第1天开始 | 2026年10月21日15:00 |
| 第2天开始 | 2026年10月22日00:00 |
| 最后一天（第31天）开始 | 2026年11月20日00:00 |
| 月卡到期 | 2026年11月21日00:00 |

月末开通的例子（运营时区的日期）：

| 开通日 | 到期日（00:00失效） | 一期天数 |
| --- | --- | --- |
| 2026年1月31日 | 2026年2月28日 | 28天 |
| 2028年1月31日 | 2028年2月29日 | 29天 |
| 2026年3月31日 | 2026年4月30日 | 30天 |
| 2026年12月31日 | 2027年1月31日 | 31天 |

同一天23:59开通的用户，也在同一个到期日期的00:00到期。首日只有不足1分钟，因此首日奖励采用开通即自动发放，避免用户因为支付接近零点而来不及领取。

### 2.2 时区来源

时区只有一个来源：用户所属的运营大区。大区对应的时区以运营中台确认的为准，大厅后台保存同一份大区与时区的映射；两边不一致时先阻止新订单、修好配置。不提供按月卡配置单独覆盖时区的做法，也不用设备时间。

采用具有地区规则的时区标识，例如Asia/Shanghai、Asia/Jakarta；日期计算遵循该时区的日历规则。没有有效运营地区或时区时，先阻止新订单并修复配置，不能默认用设备时间。

本期月卡记录开通时的运营地区、时区及来源，整个已购周期保持不变。用户旅行、修改手机时间、切换设备、改变网络位置，不改变当前月卡的奖励日期或到期时间。

后台变更地区时区只影响后续新开通。已存在自动续费订阅默认继续沿用原订阅约定；确需迁区时另设迁移生效时间和衔接规则，不能通过切区重复领取奖励。

运营地区用于游戏日期规则，商店地区用于判断支付渠道能力，二者应分别记录。

### 2.3 三组时间必须分别展示

| 时间 | 用途 |
| --- | --- |
| 配置允许新开通的起止时间 | 决定谁可以新购买这套配置 |
| 用户本期月卡起止时间 | 决定该用户本期权益及领奖资格 |
| 支付渠道的订阅及扣费时间 | 决定自动扣款、取消、宽限和支付状态 |

配置停止销售，不会让已开通用户提前到期。

## 三 支付方式与降级流程

### 3.1 支付方式

| 方式 | 展示时机 | 自动续费 | 用户提示 |
| --- | --- | --- | --- |
| 原生订阅 | 优先展示当前可用的原生订阅 | 以真实订阅约定为准 | 明示价格、计费周期、自动续费状态和管理入口 |
| 充值购买 | 原生明确失败或不可用后 | 否 | 本次为单次购买，到期后需手动购买 |
| 第三方支付 | 原生明确失败或不可用后 | 否 | 本次为单次购买，到期后需手动购买 |
| 金币购买 | 前述现金渠道均明确失败或不可用后 | 否 | 明示金币数量，确认后扣除，到期不自动扣金币 |

充值购买和第三方支付属于同一降级层，可以按运营地区配置优先顺序。用户不需要逐一尝试后台已经确定不可用的渠道；存在可用但尚未尝试的上层渠道时，不自动视为全部不可用。

现金价格来自对应渠道实际商品或已确认报价，不按客户端临时汇率自行换算。原生订阅的首版定价是 1.99 美元/月，商品信息见第十四节。金币价格独立配置为正整数，并与当前奖励版本一同展示。

同一配置版本通过不同付款方式购买，默认获得相同的奖励及领取规则（一期天数相同，用的奖励表也相同）。若运营需要差异化权益，应建立独立配置并在付款前展示，不能付款后根据渠道临时减少奖励。

### 3.2 支付渠道可用性

后台或支付中台先按客户端平台、分发渠道、商店地区及已开通的支付能力确定允许展示的渠道，再执行降级顺序。

Apple及Google的数字商品替代支付规则存在地区和项目条件；原生支付失败本身不会自动产生第三方支付资格。因此“原生失败后提供第三方”应理解为“在本渠道允许的方式内降级”，金币兑换也不能被当作不受渠道条件约束的外部充值入口。[Apple支付规则](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)；[Google Play支付规则](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en)。

### 3.3 失败与待确认

| 支付结果 | 产品处理 |
| --- | --- |
| 确认成功 | 核实订单并开通月卡 |
| 明确失败 | 提供重试及下一层允许的付款方式 |
| 当前渠道不可用 | 跳过该渠道，进入下一层允许的方式 |
| 用户取消 | 结束本次支付，可让用户主动选择其他允许方式；不自动扣款 |
| 处理中、待验证、超时未知 | 显示处理中并查单，不直接认定失败 |
| 交易已扣款但权益未到账 | 自动核对、补开或退款，并向用户展示处理状态 |

关闭弹窗或网络超时不能单独作为金币付款的解锁条件。金币兜底资格由服务端根据上层渠道真实状态确定。

每次更换支付方式都重新展示应付金额、权益及是否自动续费，并由用户确认。不得在原生失败后直接扣平台余额，或在第三方失败后直接扣金币。

### 3.4 充值与购买的关系

如果“充值”只是给平台钱包增加余额：

1. 充值到账与购买月卡是两件事。
2. 月卡需要有独立的购买确认和扣款记录。
3. 充值成功但月卡购买失败时，余额仍保留；不能显示月卡已经开通。
4. 若充值流程本身就是购买月卡商品，则以该商品订单成功作为开通依据。
5. 如果充值得到的是游戏金币，再用金币购卡，应归入金币购买方式，不能同时计为现金购买月卡。

### 3.5 金币购买

金币付款弹窗展示金币价格、可用余额、扣除后余额、完整奖励说明、具体到期时间及“不自动续费”。

确认时核对余额。金币实际扣除和月卡开通必须关联成功：扣除失败不得开卡；发生异常时必须补开或退回原扣除金币，不得形成长期有扣款无权益的状态。

金币不足时不给予开通，不允许先发首日奖励再用该奖励抵扣本次售价。

## 四 月卡配置管理

### 4.1 配置字段

| 字段 | 产品含义 |
| --- | --- |
| 活动ID | 游戏月卡活动入口及活动归属 |
| 月卡类型或商品组 | 判断是否属于同一种不可叠购权益 |
| 配置ID | 唯一标识一套运营方案 |
| 配置版本 | 记录该方案的奖励、价格、规则版本 |
| 配置名称 | 便于运营区分地区、档位和活动批次 |
| 适用运营地区 | 哪些地区的用户可以命中 |
| 适用平台及渠道 | 哪些客户端和分发渠道可以使用 |
| 适用用户范围 | 全体用户、指定人群或已有分群 |
| 配置优先级 | 处理明确设计的范围重叠 |
| 允许新开通开始时间 | 到达该时刻后允许新开通 |
| 允许新开通结束时间 | 到达该时刻即停止新开通 |
| 配置时间所属时区 | 起止时间按每个适用大区各自的时区解释（本地时间相同，UTC 时刻不同），后台预览显示各大区对应的 UTC 时刻 |
| 用户权益时区来源 | 跟随中台、大厅映射或明确覆盖 |
| 现金渠道商品信息 | 商品标识、币种、渠道报价及适用范围 |
| 金币价格 | 金币兜底购买所需数量 |
| 奖励表 | 一张31天的兜底表，加按一期实际天数（28、29、30、31天）各一张的表；每张表是第1天到最后一天对应的资产与数量 |
| 领奖规则 | 首日自动、后续手动及漏领规则 |
| 自动续费奖励策略 | 默认沿用已订阅版本 |
| 配置状态 | 草稿、待生效、可售、暂停新增、已结束、归档 |
| 操作记录 | 创建、发布、停止新增及版本变更的记录 |

### 4.2 奖励表编辑

奖励表按一期的实际天数配：

- 必须先配一张31天的兜底表。
- 再按28、29、30、31天分别配表。哪个天数没配，这一期就取兜底表的前N天（N是这一期的实际天数）。
- 每张表有两种配法：全部相同（配一次，一键填满）；逐日配置（单独设置每天，也可以批量填充指定天数后局部调整）。
- 每天可以包含金币、道具等多项奖励。后台展示每张表的完整预览和各类资产合计。
- 取兜底表前N天时，会截掉后面的天数（例如28天的月份拿不到第29到31天）。后台预览要明确列出被截掉的是哪几天、这几天有什么奖励，发布时给警告，运营确认后才能发布。
- 一期的奖励表在这一期开始时就定下，之后改配置不影响这一期。

发布前检查：

1. 兜底表必须是完整的31天，不缺天、不重复日序号；已配的28、29、30天的表同样要完整。
2. 每项奖励资产有效，数量满足资产规则。
3. 默认每日都有奖励；若未来允许空奖励日，必须明确展示，不能把空值当成正常奖励。
4. 金币价格及现金商品信息完整，至少有一条当前范围内可用的购买路径。
5. 开通结束时间晚于开始时间，地区与时区有效。
6. 匹配规则能够得到唯一结果。
7. 价格、奖励、领取规则在客户端展示与订单记录中一致。

### 4.3 修改与停用

草稿允许修改。配置一经发布，奖励、售价承诺、有效期口径和领奖规则即固定；运营调整这些内容时建立新版本。已生成但尚未支付的有效订单也保留原承诺，不能因尚无成功购买就改写其版本。

配置结束、暂停新增或下架，只停止新用户购买。已有用户继续按照已购买版本领取，直到其本期到期或出现有效退款、撤销。

历史有订单或用户绑定的配置不能直接删除，只能归档。独立客服补偿必须保留补偿理由和记录，不能通过改写整套旧配置影响所有用户。

## 五 多配置匹配与用户绑定

### 5.1 新开通匹配

新开通按照以下顺序确定配置：

1. 取得用户运营地区、平台、渠道和人群范围。
2. 筛选已发布且允许新开通的配置。
3. 校验当前时间处于配置允许的区间：包含开始时间，不包含结束时间。
4. 应用明确的人群规则及优先级。
5. 最终只允许命中一套配置。
6. 把配置ID、版本、完整奖励、价格和领取规则记录到订单；开通后绑定到本期月卡。

同一范围可以排期多条配置；不同地区或人群可以并行。若同一用户同一时刻会命中多个同优先级配置，禁止发布；运行中出现异常冲突时停止新下单并提示运营处理，不能随机选一条。

没有符合条件的配置时，不创建新购买订单。已有月卡用户仍然可以进入页面领取原本权益。

### 5.2 前端展示与开通一致

付款前展示的配置、订单记录的配置及最终绑定的配置必须一致。不得在扣款后再次按“当前最新配置”重新选择，导致用户买A得到B。

用户在配置A有效期内成功开通，就绑定A的具体版本；配置B随后开始销售，不影响该用户本期。

### 5.3 跨配置截止时间的订单

订单的支付截止时间不得晚于配置允许新开通的结束时间，并在支付前展示失效提示。

- 截止前已经真实支付成功，仅支付通知晚到：按原订单配置履约；不能由于通知晚到换成新奖励。
- 截止时仍未支付成功：关闭订单并停止继续支付，用户返回后重新确认当时可售配置。
- 订单关闭后渠道仍实际扣款：进入异常退款处理，不默默把用户换绑到新配置。
- 退款不能即时完成时展示处理中，并在后台保留未处理记录。

已核实的真实支付成功时间用于确定开通业务时间，金币购买使用扣除成功时间；订单创建时间、客户端点击时间不能代替开通时间。

由系统通知延迟造成的已付费奖励损失，按照原配置补发并记录异常原因；该补发与用户个人漏领区别处理。

## 六 每日奖励

### 6.1 奖励日序号

第N天由“当前运营日期”与“开通运营日期”的日期差加1计算。

例如10月21日开通，10月23日就是第3天，无论用户此前领取过几次、登录过几次。不能把月卡实现成“累计登录若干次”或“领完前一天才解锁下一天”。

### 6.2 首日和后续奖励

- 第1天：首次开通或新一期开始后自动发放，并显示已领取。
- 第2天起到最后一天：当天00:00开放当日奖励，用户手动点击领取。
- 每期每一天只能领取一次。
- 领取多项资产时，所有资产要么完整到账，要么处于可恢复的处理中；不能一部分到账后重试又把已到账部分重发。
- 对于已经确认的领取，网络失败重试返回原结果，不创建另一份奖励。

首日自动发放失败不影响已支付权益成立。系统继续补发该份固定奖励，不能改发当前日期对应奖励来替代首日奖励。

### 6.3 漏领及跨日

本方案默认用户未在当日领取的第2天起的奖励，到次日失效：

- 不补领。
- 不累积到下一天。
- 不延长月卡。
- 月卡到期后不再领取本期普通未领奖励。

展示一期总奖励时，应注明“按规则领取可得”，不能把需要每日领取的最大值写成无条件全部到账。

领取所属日期以服务端受理并确认资格的时间为准。23:59:59已经确认的有效领取，即使资产到账晚于00:00，也应完成；仅客户端在零点前点击、服务端零点后才收到的请求，按实际受理日期判断。

系统确认过的领取和系统故障补发，可以在原领取窗口结束后完成；不因此重新打开普通补领入口。

### 6.4 多端与跨账号

同一账号在多台设备登录，共享月卡与领取记录。重复点击、并发请求、恢复购买，不增加奖励次数。

一笔原生交易只能绑定一个确定的业务账号。更换账号或设备后恢复购买，应核对原归属，不能将同一笔付款复制到多个账号。

## 七 续费与重复购买

### 7.1 单次购买

充值购买、第三方支付和金币购买都不自动续费。

有效期间默认不开放同类型月卡手动再次购买。到期后，用户按照当时有效配置重新购买，付款成功后从新的开通日期重新算一个自然月，奖励从第1天重新开始，用的奖励表按新一期的实际天数选。

过期到重新购买之间没有月卡权益，也没有对应奖励。页面必须明确提示“到期后需手动再次购买”。

提前预购、叠加天数、同时持有多张同类型月卡，不属于首版默认规则。

### 7.2 支持对应周期的自动续费

本条适用于原生订阅（Apple、Google）和支持按月续费的中台订阅。

- 每个已确认成功的续费账期对应一份本期权益记录。
- 提前确认的下一期不立即发放首日奖励，在约定的新一期开始时间生效。
- 下一期与上一期按约定连续衔接，不能因为通知重复而叠加额外天数。
- 通知晚到但渠道已经按约定及时成功扣款，按实际成功周期补齐权益和系统造成的漏发。
- 用户取消自动续费只影响未来扣款，当前已经付费的本期继续有效。
- 续费失败且没有有效的宽限权益时，不能凭自动续费开关直接生成新的已付费周期。
- 一期的起止以商店返回的到期时间为准，不自己推算；日期按用户所属运营大区的时区转换。
- 续费日当天算下一期的第1天，上一期最后一个奖励日是续费日的前一天，同一天不会领两份奖励。
- 续费日锚定第一次订阅的日期：1月31日首次订阅，之后依次是2月28日、3月31日、4月30日、5月31日，短月缩短一期，下个月回到31号。单次购买到期后重新购买不带这个锚点，从新的开通日重新算。
- 每一期用这一期实际天数对应的奖励表，续费确认时定下；续费成功时发放下一期第1天的奖励。

### 7.3 续费时使用哪套配置

补充默认：

| 情况 | 奖励配置 |
| --- | --- |
| 本期还有效，运营发布新配置 | 本期继续原版本 |
| 原生订阅按原约定自动续费 | 沿用该订阅已约定的奖励版本 |
| 单次月卡到期后手动重新购买 | 使用重新购买时匹配的配置 |
| 原订阅真正终止后重新订阅 | 作为新开通匹配当时配置；平台恢复原合同的情形另按真实合同处理 |

配置销售截止不等于已有订阅合同终止。需要停止某套配置的后续订阅时，运营必须另外处理已有续订用户，并告知后续安排；不能在商店继续扣款的情况下停止兑现奖励。

如果希望自动续费也始终切到最新配置，必须另外配置迁移规则、用户提前可见说明和必要的确认流程；尤其不能在用户不知情时减少持续订阅的奖励。

### 7.4 扣款重试、宽限与换渠道

首次购买失败和后续自动续费失败分开处理。Apple和Google都存在续费失败后的状态恢复机制，部分配置下用户在宽限期间仍保有权益，不能仅收到一次失败通知就认为订阅彻底结束。[Apple订阅状态与宽限说明](https://developer.apple.com/app-store/subscriptions/)；[Google订阅生命周期](https://developer.android.com/google/play/billing/lifecycle/subscriptions)。

在仍有有效权益、付款状态未知或原生仍可能恢复扣款时，页面先显示真实状态及管理订阅入口。用户改为手动付款前，需要核实原订阅停止续费或终止的实际结果，不能只靠本地关闭一个开关认定商店不会再扣款。

如仍出现两条渠道真实付款成功，应保留两笔交易并启动重复购买售后处理。默认不静默叠加月卡；能够退款的多余订单按原渠道退款，受渠道能力限制的退款展示处理进度并由客服跟进，不能丢弃已收款事实。

同一笔交易重复通知只处理一次；两笔不同的成功付款不能混同为重复通知。

## 八 金币与其他大厅活动的关联

### 8.1 月卡不参与净消耗

月卡奖励到账的金币不算“获得”，用金币购买月卡也不算“支出”。月卡的收支都不进净消耗，明日宝箱和金币随机礼包算资格时，里面没有月卡的钱。（这两个活动计入的只有游戏、宝箱的买箱/奖励/过期退款、礼包的额外赠送，见它们各自的文档。）

这样买卡花的金币不会被当成又输了钱，领卡奖励也不会拉低别的活动的资格。以后如果要让月卡奖励参与净消耗，必须把购卡支出一起计入，保持两边对称，并且和宝箱、礼包文档、后端文档一起改。

### 8.2 金币购卡不是游戏输钱

使用金币购买月卡属于购买权益的支出。该支出会减少钱包余额，但不计入“游戏输钱”或“游戏净消耗”。

例如：

| 事项 | 对相关游戏净消耗的影响 |
| --- | --- |
| 用户已有游戏净消耗10,000金币 | 基础值为10,000 |
| 使用3,000金币购买月卡 | 仍为10,000，不增加到13,000 |
| 领取月卡奖励600金币 | 仍为10,000，不会减到9,400 |

充值本金、月卡购卡支出、月卡奖励及退款冲正分别记录，都不进净消耗口径；退款撤回已发月卡奖励时，在钱包里对原奖励做相应冲正。

### 8.3 奖励预算

后台显示金币售价、一期的金币奖励总量、其他奖励总量以及已发放金额或数量。

允许运营观察“金币奖励能否覆盖再次购卡成本”，但不自动禁止奖励高于售价。是否允许这种持续兑换关系属于运营策略，应由运营结合现金收入和金币投放预算设置。

## 九 用户页面

### 9.1 未开通

展示月卡名称、当前可购买配置的奖励日历、按规则可领取的总奖励、当期价格、日期规则、所属运营时区、领取及漏领说明。

默认展示原生订阅入口，按允许渠道和失败状态进入后续付款方式。若当前没有可购买配置，显示活动暂未开放，不影响已有用户领取。

### 9.2 已开通

展示：

- 本期生效时间和明确的到期时间。
- 所属运营地区及时区。
- 当前是第几天。
- 今日奖励及领取状态。
- 本期奖励日历（第1天到最后一天）：已领取、今日可领、未来未开放、历史已过期。
- 本期已领取奖励。
- 支付方式与自动续费状态。
- 原生订阅管理或恢复购买入口。
- 本期实际绑定的奖励内容，不能用当前新售配置覆盖用户已购内容。

### 9.3 到期与异常

到期页面显示上期已结束、历史领取情况及当前可重新购买的方案。手动购买用户明确显示需要重新付款。

支付处理中、奖励处理中、退款处理中分别显示，避免把技术处理中的订单提示为需要再付一次款。

### 9.4 关键文案

| 场景 | 文案示例 |
| --- | --- |
| 充值或第三方购买 | 本次为单次购买，不会自动续费。月卡到期后，需要你手动再次购买。 |
| 金币购买 | 确认消耗X金币开通月卡？本次购买不会自动续费。 |
| 日期说明 | 开通当天计为第1天，到期日00:00到期（开通日加1个月的同一号，没有就取当月最后一天），一期28到31天，按所属运营地区时间计算。 |
| 奖励说明 | 首日奖励开通后自动到账；其余奖励需在对应日期领取，错过不补发。 |
| 原生付款处理中 | 正在确认付款结果，请稍后查看订单状态。 |
| 取消自动续费 | 已关闭后续自动续费，本期权益保留至显示的到期时间。 |

原生订阅文案必须使用该渠道真实价格、计费周期和订阅状态；文案写“每月自动续费”，不要写“每30天”。

## 十 后台查询与运营统计

### 10.1 用户维度

输入用户ID后，展示当前本期月卡及历史月卡：

| 信息组 | 内容 |
| --- | --- |
| 用户 | 用户ID、运营地区 |
| 当前绑定 | 活动ID、月卡类型、配置ID、版本、配置名称、本期月卡标识 |
| 时间 | 开通时间、到期时间、运营时区、当前第几天 |
| 支付 | 支付方式、订单、实际支付金额或金币、支付状态 |
| 订阅 | 自动续费开关、渠道订阅状态、下一账期信息 |
| 奖励 | 今日状态、每日领取明细、已发奖励、漏领、补发和冲正 |
| 售后 | 退款、撤销、重复购买和异常处理记录 |

运营必须一眼区分“当前正生效的是哪个版本”和“用户历史买过哪些版本”。

### 10.2 配置维度

| 指标 | 统计口径 |
| --- | --- |
| 当前生效用户数 | 统计时点本期权益有效且未撤销的去重用户数 |
| 当前生效期数 | 有效权益期数，单独于人数记录 |
| 当前生效用户列表 | 与当前生效人数使用相同条件 |
| 累计开通用户数 | 历史曾成功开通该版本的去重用户数 |
| 累计开通期数 | 成功购买或续费形成的期数，同一用户可贡献多期 |
| 已到期期数 | 到期且未由退款撤销归类的期数 |
| 退款或撤销期数 | 独立分类，不混入正常有效期数 |
| 当前自动续费用户数 | 当前订阅仍约定自动续费的去重用户数 |
| 实收金额及金币 | 分渠道、分币种列示，扣除已完成退款 |
| 已发奖励 | 按实际到账资产统计，并展示撤回或冲正 |
| 今日可领未领人数 | 当前符合当日领奖资格且尚未完成领取的人数 |
| 待履约奖励预算 | 当前有效期中今日未领及未来奖励的最大承诺数量 |

当前生效用户数必须按查询时点计算，不能因用户未登录或状态尚未刷新而把已经到期用户继续计入。

按渠道宽限仍应保留权益的用户，如实际启用商店订阅版，应单独标记宽限状态并按实际有效性统计。

累计开通用户保留曾开通过的事实，后续退款另外列示；可另提供“排除全额退款后的净付费用户数”，不能让一个指标在不同页面使用不同含义。

各配置的累计用户可能重叠，不可直接相加当作全活动去重用户数。

### 10.3 名单操作

从配置点击人数，进入对应用户列表，可按用户ID、配置版本、地区、支付方式、有效状态、开通日期、到期日期及今日领取状态筛选。

支持查看用户详情和导出当前筛选结果。导出记录统计时间、筛选条件及时区，使名单和人数可核对。

### 10.4 配置示例

以下为示例，不是实际用户数据。均按Asia/Shanghai：

| 配置 | 允许新开通的时间 |
| --- | --- |
| A | 2026年10月1日00:00至2026年11月1日00:00，不含结束时刻 |
| B | 2026年11月1日00:00至2026年12月1日00:00，不含结束时刻 |

用户甲于10月21日15:00购买A，本期到11月21日00:00结束；用户乙于11月2日12:00购买B，本期到12月2日00:00结束。

11月10日查询时，两位用户都有效。A虽然已经停止新增，仍有当前生效用户甲；B有当前生效用户乙。不能因为当前可售配置是B，就把用户甲统计到B。

## 十一 退款 撤销与异常处理

| 事项 | 处理规则 |
| --- | --- |
| 取消自动续费 | 只停止未来续费，本期已经付费的权益继续 |
| 明确付款失败 | 不开卡、不发首日奖励 |
| 交易成功但开通失败 | 自动核对并补开；不能要求用户重复付款解决 |
| 全额退款且明确撤销本期权益 | 停止未发奖励，记录撤销时间及原因 |
| 渠道仅退款、未撤销或部分退款 | 按真实售后结果处理，不自动假定全部权益失效 |
| 已发奖励追回 | 记录可追回数量、已追回数量及无法直接追回部分 |
| 余额不足追回 | 进入售后处理；不在无规则情况下静默制造负余额 |
| 金币购卡退款 | 恢复购卡支出时同步处理已发奖励及冲正，防止反复领奖退款 |
| 系统故障漏发 | 按原配置补发原应得奖励，保留原因和原所属日期 |

具体能否退款、退款比例和渠道限制，按已经制定的售后政策执行；本文不默认所有渠道都支持无条件自动退款。

如果已退款或撤销的旧支付通知再次到达，不得重新开卡或再次发奖。所有状态变化保留来源和时间，便于客服核查。

| 30 | 续费日当天 | 算下一期第1天，同一天不领两份奖励 |
| 31 | 一期内用户所属大区变化 | 本期时区和到期时间不变 |
| 32 | 单次购买到期后重新购买 | 从新的开通日重新算一个自然月，不沿用老的日期 |

## 十三 原生订阅与自然月

原生订阅（Apple、Google）按自然月续，和本文的自然月规则一致，不再需要在“严格30天”和“保留自动续费”之间二选一。接入时还要核对四件事：

1. 一期的起止以商店返回的到期时间为准，不自己推算。
2. Google“每月”遇到月末（例如31号）怎么处理，官方页面没写，用测试账号核对。Apple的规则是没有那一天就取当月最后一天，之后回到原来的日期。
3. 商店的扣款时间点一般不是0点（比如15:00），而我们的奖励日按运营大区的0点切。续费日当天算下一期第1天，续费成功时发第1天的奖励；续费日0点到扣款成功之间，用户还在上一期的权益时段，没有新的奖励日。
4. 商店的宽限期、账户保留期内，权益和奖励是否继续发放：按7.4的原则以渠道真实状态为准，接入前要定下来。
